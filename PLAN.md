# PLAN.md — разбивка фаз 3–7 на подфазы

Источник требований — `MyBuild_NestJS_TZ.md`. Правила работы — `CLAUDE.md`. Журнал — `progress.md`.

Фазы 0–3 завершены (см. `CLAUDE.md` §6). Этот файл покрывает то, что осталось; разбивка Фазы 3 оставлена как образец состава подфазы.

---

## Что это за файл

**`PLAN.md` — рекомендация, а не истина.** Источник требований — ТЗ (`MyBuild_NestJS_TZ.md`), правила работы — `CLAUDE.md`. Этот файл лишь разбивает фазы ТЗ на подфазы: он писался до кода и местами угадывает.

Отсюда правило для агента: **опираться на этот файл, а не следовать ему буквально.** Если по ходу работы видно, что пункт подфазы неверен, устарел или противоречит ТЗ, — агент решает сам и делает как правильно, а в `progress.md` пишет, что и почему изменил. Спрашивать пользователя нужно тогда, когда расхождение важное: меняется контракт API, схема БД, модель доступа или объём подфазы.

Чего делать нельзя: молча выкидывать пункт, потому что он оказался неудобным. Отступление либо обосновано в `progress.md`, либо это не отступление, а пропуск работы.

С ТЗ так нельзя: расхождение с ТЗ — это `CLAUDE.md` §4, «увидел — сказал — договорились — сделал».

---

## Правила прохождения (важнее всего)

1. **Одна подфаза за подсессию.** Агент берёт ровно одну подфазу, доводит её до DoD и останавливается. Не «заодно начну следующую».
2. **Начало подсессии:** прочитать `progress.md`, затем этот файл, затем нужный раздел ТЗ. Только потом код.
3. **Конец подсессии:** дописать в `progress.md` блок из четырёх частей — «сделано / принятые решения / что дальше / где грабли» — и дать в чат короткий отчёт.
4. **В отчёте указать одно из двух:** «в фазе N осталось: …» или «фаза N завершена целиком».
5. **Не спрашивать «делать дальше?».** Отчёт закончен — работа остановлена. Следующую подфазу начинать только по явному указанию пользователя.
6. **DoD подфазы проверяется, а не заявляется** (`CLAUDE.md` §2): сборка, типы, линтер, тесты прогнаны; endpoint дёрнут; экран открыт.
7. Подфаза не «переносится частично»: если что-то из неё не сделано — это пишется в `progress.md` в «что дальше», а не замалчивается.

## Фаза 3 — Заказы клиента (5 подфаз)

Самая объёмная фаза: здесь появляется и работа с файлами, и первый настоящий CRUD, и три больших экрана.

### 3.1 — Модуль `files`: Supabase Storage

- Приватный бакет в Supabase, ключи в `.env` (`service_role` только на backend).
- `FilesService`: загрузка в Storage, санитизация имён, MIME-allowlist (PDF, DWG, PNG/JPEG), лимит 20 MB, SHA-256 и дедупликация в пределах одной сдачи, выдача signed URL.
- Запись `OrderFile` (`ownerType`, `submissionRound`, `fileHash`, `originalName`, `mimeType`, `sizeBytes`).
- Проверка доступа к файлу: участник заказа (клиент заказа либо компания с принятым предложением).
- Unit-тесты на валидацию и дедуп; ручная проверка «загрузил → получил signed URL → скачалось».

**DoD:** файл реально лежит в бакете, строка `OrderFile` создана, signed URL открывается, чужой файл не отдаётся.

### 3.2 — Backend `orders`: CRUD

- `POST /orders` — все поля §4.1, multipart с файлами, `ownerType = CLIENT`, `submissionRound = 0`, статус `WAITING`.
- `GET /orders?status=&q=&page=` — свои заказы, фильтр по статусу, поиск по `ORD-7829`/`7829`/названию/подрядчику, пагинация.
- `GET /orders/:id` — ролезависимый ответ (§4.1 «Приватность и видимость»).
- `DELETE /orders/:id` — только свой заказ и только в `WAITING` / `AWAITING_CONFIRMATION`.
- `OwnershipGuard` (§9) — здесь его первое применение.
- `@nestjs/throttler` на мутирующих маршрутах (§6).
- e2e: создание с файлом, поиск, пагинация, 403 на чужой заказ, 409 на удаление заказа в работе.

**DoD:** все четыре маршрута отвечают на живой базе, права проверены тестом.

### 3.3 — Frontend: список заказов

- Браузерный API-клиент (`lib/api.ts` + обёртка, берущая токен из сессии Supabase) — в Фазе 2 была только серверная.
- `/orders`: заголовок, кнопка «Создать заказ», поиск, вкладки статусов, таблица (Заказ / Подрядчик / Статус / Бюджет / Срок), пагинация «Показано N из M».
- Адаптив: таблица на десктопе → карточки на мобильном.
- `StatusBadge` по цветам §3, skeleton и empty-state.

**DoD:** экран открыт в браузере на seed-данных, поиск и вкладки работают, мобильная ширина не ломается.

### 3.4 — Frontend: создание заказа

- `/orders/new`: две колонки — «Детали проекта» (название, категория, тип объекта, площадь, описание, файлы drag&drop) и «Бюджет и Локация» (бюджет, желаемая дата начала, адрес).
- `FileDropzone`: превью, удаление до отправки, клиентская проверка размера и типа.
- Валидация формы на русском, зеркальная DTO бэкенда; `desiredStartDate` не раньше сегодня.
- Кнопки «Отмена» / «Опубликовать заказ», тост об успехе, переход на созданный заказ.

**DoD:** заказ создаётся из браузера вместе с файлами и появляется в списке.

### 3.5 — Frontend: детали заказа

- `/orders/[id]`: описание, площадь (плюс «уточнено исполнителем», если есть), адрес, сроки, бюджет/цена, файлы клиента со скачиванием.
- Места под то, что появится в Фазе 4 (предложения, сдачи), — заранее размеченные пустые блоки, а не «доделаем потом» в стиле ad-hoc.
- Удаление заказа с подтверждающим диалогом, кнопка видна только в разрешённых статусах.
- Хлебные крошки, 404 на чужой/несуществующий заказ.

**DoD:** клиент создаёт заказ с файлами, находит его поиском, открывает детали, скачивает файл, удаляет заказ — весь DoD Фазы 3 из ТЗ пройден в браузере.

## Фаза 4 — Предложения и полный цикл сделки (5 подфаз)

Каждая мутация здесь идёт через `OrderStateMachine` и `OrderTransitionService` — новых мест с логикой статусов не появляется.

### 4.1 — Backend: лента и предложения

- `GET /company/orders/available?q=&page=` — `WAITING` + `AWAITING_CONFIRMATION`, где у компании нет предложения либо оно `WITHDRAWN` / `REJECTED` (§4.1, условие обязательное).
- `GET /company/offers?status=&page=`.
- `POST /offers` — upsert по `@@unique([orderId, companyId])`, возврат статуса в `SENT`, переход заказа `WAITING → AWAITING_CONFIRMATION`.
- `POST /offers/:id/withdraw` (компания), `POST /offers/:id/reject` (клиент) — с переходом заказа обратно в `WAITING`, если активных предложений не осталось.
- e2e: компания отозвала предложение → заказ снова виден в ленте → подала новое.

**DoD:** лента и все четыре маршрута работают, отзыв/отклонение корректно возвращают заказ в `WAITING`.

### 4.2 — Backend: сделка и приёмка

- `POST /orders/:id/accept-offer/:offerId` — `price`, `deadline`, прочие офферы в `NOT_ACCEPTED`.
- `POST /orders/:id/submit` — сдача работы, `submissionRound + 1`.
- `POST /orders/:id/files` — файлы компании + обязательный комментарий, версионирование по сдачам.
- `PATCH /orders/:id/verified-area` — только компания-исполнитель, только в трёх статусах, статус и цену не меняет.
- `POST /orders/:id/confirm`, `POST /orders/:id/dispute` (+ `correctionComment`).
- e2e: полный цикл до `COMPLETED` через доработку.

**DoD:** весь путь заказа проходится запросами к API на живой базе.

### 4.3 — Frontend: кабинет компании

- `/available`: лента доступных заказов с `clientBudget` клиента, поиск, пагинация.
- Форма предложения (цена, срок, комментарий) — диалог или страница, upsert-семантика видна пользователю («обновить предложение»).
- `/offers`: свои предложения по статусам, отзыв предложения.

**DoD:** компания из браузера находит заказ, отправляет и обновляет предложение, отзывает его.

### 4.4 — Frontend: клиент выбирает и принимает

- На `/orders/[id]`: список активных предложений (название компании, цена, срок, комментарий), сравнение, «Принять» / «Отклонить» с подтверждением.
- После принятия — блок принятого предложения, цена сделки и срок.
- Кнопки «Подтвердить выполнение» и «Отправить на доработку» (диалог с `correctionComment`), доступные строго по статусу — состав кнопок берётся из `OrderStateMachine.can()`.

**DoD:** клиент в браузере принимает предложение, подтверждает работу и отправляет на доработку.

### 4.5 — Frontend: сдача работы и история сдач

- Компания на `/orders/[id]`: загрузка файлов + обязательный комментарий, кнопка «Сдать работу», уточнение площади.
- Показ последней сдачи по умолчанию, сворачиваемый блок «История сдач».
- `correctionComment` виден нужной стороне.
- Сквозная проверка DoD Фазы 4 в браузере на двух аккаунтах, включая приватность §4.1: компания видит только своё предложение, а заказ без своего участия — как `WAITING`.

**DoD:** полный цикл проходится двумя реальными пользователями в браузере, без обращений к API вручную.

## Фаза 5 — Real-time и уведомления (4 подфазы)

### 5.1 — Backend: эндпоинты уведомлений

- `GET /notifications?unread=&page=`, `GET /notifications/unread-count`, `POST /notifications/:id/read`, `POST /notifications/read-all`.
- Проверка, что записи, которые уже пишет `OrderTransitionService`, покрывают все типы `NotificationType` из §3.
- e2e на чужие уведомления (403/пустой список).

**DoD:** уведомления читаются и помечаются прочитанными через API.

### 5.2 — Backend: `OrderGateway`

- Socket.io, namespace `/ws`, авторизация handshake-токена той же проверкой по JWKS.
- Комнаты `user:{id}`, `order:{id}`, `company-feed`; правила входа в комнату заказа — только участники.
- Эмит всех событий §8 после коммита транзакции перехода (`OrderTransitionService` уже возвращает всё нужное).
- `order:created` — только broadcast, записей в БД не создаёт.

**DoD:** события видны в тестовом сокет-клиенте; неавторизованный сокет отклонён.

### 5.3 — Frontend: подписка и живое обновление

- `lib/socket.ts` — подключение с токеном, переподключение, отписка при уходе со страницы.
- Обновление списков заказов, ленты компании и деталей заказа по событиям, без reload.
- Оптимистичные мутации подтверждаются событием (§7 «UX-замечания»).

**DoD:** действие в одном окне браузера видно во втором окне другой роли без перезагрузки.

### 5.4 — Frontend: колокольчик и раздел «Уведомления»

- Счётчик непрочитанных в шапке, живой по `notification:created`.
- `/notifications`: непрочитанные сверху, «Прочитать все», клик → переход к заказу.

**DoD:** уведомления копятся офлайн и видны после переподключения; счётчик сходится с API.

## Фаза 6 — Подрядчики, документы, настройки (4 подфазы)

### 6.1 — Backend: `/contractors` и `/documents`

- `GET /contractors?q=&page=`, `GET /contractors/:id` (название, город, контакты, число завершённых заказов) — роль `CLIENT`.
- `GET /documents?ownerType=&orderId=&page=` — все файлы пользователя по всем его заказам.
- `GET /documents/:id/download` — signed URL с проверкой участия в заказе (переиспользует `FilesService` из 3.1).
- e2e на доступ: чужой документ не отдаётся, компания не видит каталог подрядчиков.

**DoD:** оба раздела отдают данные и корректно закрыты по ролям.

### 6.2 — Frontend: подрядчики

- `/contractors`: список с поиском, карточка компании.

**DoD:** клиент находит компанию поиском и открывает карточку.

### 6.3 — Frontend: документы

- `/documents`: имя, тип, размер, дата, заказ, кем загружен; фильтры (роль-владелец, заказ), скачивание.

**DoD:** любой свой файл находится, не заходя в заказ.

### 6.4 — Frontend: настройки

- `/settings`: профиль (имя, телефон, город, страна, `companyName`) через `PATCH /profile`.
- Смена пароля через Supabase SDK (`updateUser`).
- Раздел «Платежи» с пометкой «скоро» (§11).

**DoD:** профиль меняется и сохраняется, пароль меняется и новый работает при входе.
