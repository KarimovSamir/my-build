# audit_fix.md — что исправлено по `audit.md`

Журнал закрытия находок независимой ревизии (`audit.md`). Идентификаторы — оттуда же.
Подробности каждого сеанса — в `progress.md`, принятые решения — в `CLAUDE.md` §6.

## Фаза 0 — закрыта 3 сентября 2026

### Средние

**0-С1. Тёмная тема объявлена, но недостижима.** Исправлено.
Токены `.dark` в `globals.css` лежали мёртвыми: класс `dark` никто не выставлял.
Добавлен `frontend/src/components/theme-provider.tsx` (обёртка над `next-themes`:
класс на `<html>`, по умолчанию системная тема, выбор в `localStorage`) и подключён
в корневом `app/layout.tsx`. Переключатель — `frontend/src/components/theme-toggle.tsx`
(«Светлая» / «Тёмная» / «Как в системе»), стоит в шапке кабинета, в шапке лендинга
и на экранах входа, то есть доступен на всех страницах.

**0-С2. `Toaster` запрашивал системную тему.** Исправлено вместе с 0-С1.
`ui/sonner.tsx` не менялся: с появлением провайдера его `useTheme()` начал возвращать
выбор пользователя. Проверено прицельно — светлая тема при тёмной ОС даёт светлый тост.

### Низкие

**0-Н1. `lib/types.ts` без импортёров.** Исправлено.
Все 20 файлов фронта переведены с прямого `@mybuild/shared` на `@/lib/types` —
как этот файл и объявлен в ТЗ §7. Новый код фронта должен идти через реэкспорт.

**0-Н2. `lib/socket.ts` без импортёров.** Не трогали — файл ждёт Фазы 5, это не дефект.

**0-Н3. Неиспользуемые компоненты дизайн-системы.** Исправлено частично.
`ui/dropdown-menu` ушёл в переключатель темы, `ui/separator` — в шапку кабинета,
`ui/badge` — в основу `status-badge.tsx`.
**`ui/tabs.tsx` оставлен, но по-прежнему ничего не делает: его никто не импортирует.**
Решение пользователя от 3 сентября 2026 — файл не удалять. Причина, по которой он не
используется: вкладки статусов на `/orders` сделаны ссылками (выборка обязана жить
в адресе), а Radix Tabs хранит выбор в состоянии компонента. `Tabs` при этом перечислен
в списке базовых компонентов ТЗ §7. На сборку и бандл не влияет: файл не импортируется,
значит не собирается.

**0-Н4. Проп `size` у логотипа менял только размер картинки.** Исправлено.
`size` теперь шаг — `sm | md | lg`; каждый задаёт и размер картинки, и высоту на экране,
и кегль текста. Заодно ушло предупреждение консоли про `_next/image?...&w=32`.

**0-Н5. Английская подпись `Close` в `ui/dialog.tsx`.** Исправлено — «Закрыть».

**0-Н6. `frontend/README.md` — шаблон `create-next-app`.** Исправлено: README переписан
по проекту (запуск, переменные окружения, защита маршрутов, тема, структура, проверки).

**0-Н7. Корневой `typecheck` не включал `shared/`.** Исправлено: скрипт начинается
с `npm run typecheck -w shared`.

### Чем проверено

`npm run typecheck` (теперь и `shared/`), `npm run lint`, `npm run build`, `npm test`
(155 unit) — зелёное; backend не менялся, e2e не гоняли. В браузере: обе темы на кабинете,
странице заказа, диалоге удаления, лендинге и входе; сохранение выбора между переходами
и перезагрузкой; живая реакция режима «как в системе» на смену схемы ОС; светлый тост
при тёмной ОС; ширина 390 px; консоль пустая на всех проверенных страницах.

## Фаза 1 — закрыта 3 сентября 2026

### Средние

**1-С1. Дубликат списка статусов исполнителя.** Исправлено.
Локальный `EXECUTING_OFFER_STATUSES` в `OrderTransitionService` удалён. В `shared/src/offers.ts`
он теперь объявлен как самый узкий список («компания работает по заказу прямо сейчас»),
а `EXECUTOR_OFFER_STATUSES` выведен из него добавлением `COMPLETED`, `ACTIVE_OFFER_STATUSES` —
добавлением `SENT`. Новый статус исполнителя достаточно дописать в один список.

**1-С2. Проигравшие компании не получали ни уведомления, ни адресата события.** Исправлено.
Эффект `DECLINE_OTHER_OFFERS` («отклонить остальные скопом») убран. Событие `OFFER_ACCEPTED`
теперь несёт `otherOffers` — список чужих предложений в статусе `SENT` с их `companyId`,
и машина на каждое выдаёт и `SET_OFFER_STATUS → NOT_ACCEPTED`, и `CREATE_NOTIFICATION`
(`OFFER_REJECTED`, «клиент выбрал другое предложение»). Сам эффект `SET_OFFER_STATUS` получил
`companyId`, а `AppliedTransition` — поле `offerUpdates`: из него Фаза 5 берёт адресатов
`offer:status_changed` (ТЗ §8).

**1-С3. Переход по предложению не смотрел на его текущий статус.** Исправлено.
Проверка сделана в машине, а не в сервисе: `OrderEvent` теперь несёт `offerStatus`, а таблица
`OFFER_PRECONDITIONS` задаёт, из каких статусов предложения событие имеет смысл. Запрет —
`InvalidOfferStatusError` (409, `error: "InvalidOfferStatus"`). Статус заказа проверяется первым.
Повторно отклонить уже отклонённое предложение, принять отозванное или сдать работу дважды
теперь нельзя. `OFFER_SUBMITTED` разрешён из `SENT / WITHDRAWN / REJECTED / NOT_ACCEPTED`:
компания вправе прислать предложение заново, но не когда уже работает по заказу.

### Низкие

**1-Н1. `${orderId}::uuid` в сыром запросе.** Исправлено.
Проверка вынесена в `backend/src/common/uuid.ts` (`isUuid`), `OwnershipGuard` переведён на неё,
`OrderTransitionService` проверяет и `orderId`, и `offerId` до похода в базу — мусор даёт 404,
а не 500.

**1-Н2. `storageKey` в seed неправильного формата.** Исправлено.
`buildStorageKey` переехал из `files.service.ts` в чистый `file-validation.ts` и вызывается
и приложением, и seed. Заказ в seed создаётся первым, файлы — следом: в ключе нужен его id.
Проверено на живой базе: `orders/{orderId}/client/0/{хеш16}-{имя}`.

**1-Н3. Уведомление с типом `OFFER_RECEIVED` и текстом про другое предложение.** Исправлено:
тип `OFFER_REJECTED`, заголовок «Предложение отклонено», текст — тот же, что выдаёт машина.

**1-Н4. Изменяемые экспортируемые массивы статусов.** Исправлено: все три объявлены
`readonly OfferStatus[]`. Prisma ждёт изменяемый массив, поэтому в запросах идёт копия.

**1-Н5. `OrderFile` без `uploadedById`.** Оставлено как есть — **решение пользователя
от 3 сентября 2026**. `ownerType` уже отвечает на вопрос «чей файл», исполнитель у заказа один,
а колонка стала бы вторым источником правды рядом с офферами.

### Чем проверено

`npm run typecheck` (shared + backend + frontend), `npm run lint`, `npm run build`,
`npm test` — 163 unit (было 155), `npm run test:e2e` — 69 e2e (было 67), seed прогнан
и проверен запросом к базе. Подробности — в `progress.md`.

## Фаза 2 — закрыта 3 сентября 2026

### Средние

**2-С1. `GET /health` отдавал текст ошибки базы кому угодно.** Исправлено.
Поле `databaseError` из ответа убрано совсем: наружу идёт только `database: "down"`,
а причина пишется в лог (`Logger` контроллера). Заодно маршрут получил ограничение
частоты — 60 запросов в минуту на адрес: он делает настоящий запрос к базе и открыт
без токена, но по нему же будет ходить внешний пингер из §7.1.

**2-С2. `SupabaseJwtService` без тестов.** Исправлено.
`supabase-jwt.service.spec.ts` — 21 тест на настоящей паре ключей ES256 и настоящей
`jose`; подменяется только сеть, отдающая JWKS. Проверены: правильный токен, чужой
ключ, подделанная нагрузка, чужой `iss`, чужой `aud`, истёкший срок, мусор вместо
токена, отсутствие `sub`, кэширование ключей, разбор `user_role` и `email_verified`.

**2-С3. Подтверждение email не проверялось кодом.** Исправлено.
Миграция `20260903170000_email_verified_claim`: `custom_access_token_hook` кладёт
в токен claim `email_verified`, читая `auth.users.email_confirmed_at`. Значение
подписано Supabase, подделать его нельзя — в отличие от одноимённого поля
в `user_metadata`, которое пользователь меняет сам через `updateUser`.
`SupabaseAuthGuard` отвечает 403 на неподтверждённый адрес, `proxy.ts` уводит
такого пользователя на экран `/verify-email`.

**2-С4. `getHomeHref(null)` вёл на заглушку `/settings`.** Исправлено.
Появился экран `/no-role`: вход выполнен, роли в токене нет, причина названа прямо
(не включён Custom Access Token Hook), на экране кнопка «Выйти». Туда же ведёт
`getHomeHref(null)`.

### Низкие

**2-Н1. Пользователь без роли проходил на любой раздел.** Исправлено вместе с 2-С4:
`proxy.ts` больше не пропускает отсутствующую роль (`if (role && …)` убран) —
и неподтверждённый email, и отсутствие роли уводят на свой служебный экран.
Исключение — `/callback` и `/reset-password`: увод оттуда не дал бы подтвердить
адрес никогда.

**2-Н2. Телефон не проверялся по формату.** Исправлено.
`shared/src/profile.ts`: `PHONE_PATTERN` (цифры, пробелы, скобки, дефисы,
необязательный `+`, всего 10–15 цифр), `PHONE_MAX_LENGTH`, `PHONE_ERROR_MESSAGE`
и `isValidPhone`. Правило одно на форму регистрации и на DTO `PATCH /profile`.

**2-Н3. `PATCH /profile` без ограничения частоты.** Исправлено: 20 запросов в минуту.

**2-Н4. `frontend/env.example` предписывал `.env.local`.** Исправлено: шаблон
называет `frontend/.env`, а `.env.local` упомянут как место личных переопределений.

**2-Н5. `decodeURIComponent` в крошках без защиты.** Исправлено: разбор сегмента
обёрнут в `try/catch`, при ошибке показывается сегмент как есть.

**2-Н6. Крошка «Главная» вела на `/`, откуда вошедшего перекидывало обратно.**
Исправлено: «Главная» ведёт в кабинет роли (`/orders` или `/available`), а когда
первый сегмент пути и есть кабинет — крошка не показывается, чтобы не дублировать
соседнюю ссылку.

### Чем проверено

`npm run typecheck`, `npm run lint`, `npm run build` — зелёное. `npm test` — **186 unit**
(было 163), `npm run test:e2e` — **77 e2e** (было 69). Миграция применена к живой базе
Supabase и проверена: вход seed-клиента даёт токен с `user_role: CLIENT`
и `email_verified: true`, а вызов хука для неподтверждённой учётной записи —
`email_verified: false` (это же проверяет новый e2e). В браузере пройдены: вход обеими
ролями, крошки на `/orders`, `/settings`, `/documents` и странице заказа, оба служебных
экрана и все переходы к ним и от них, отказ формы регистрации на неверном телефоне.
`/health` отдаёт `{status, uptimeSeconds, database}` и 429 после 60 запросов в минуту.
