## 1. Суть продукта

MyBuild — двусторонний маркетплейс для строительства.

- **Клиент** создаёт заказ (название, категория, тип объекта, площадь, адрес, бюджет, описание, файлы), получает предложения от компаний с ценой и сроком, выбирает одно, контролирует ход работ и принимает результат (или отправляет на доработку).
- **Компания** видит доступные заказы вместе с ожиданиями клиента по бюджету, отправляет своё предложение с ценой и сроком, после принятия выполняет работу, прикладывает файлы/комментарий и сдаёт на подтверждение.

Ядро продукта — **workflow «выбор исполнителя клиентом + контроль приёмки»** с явной state-машиной заказа.

## 2. Технологический стек

| Слой | Технология | Примечание |
|------|-----------|-----------|
| Backend | **NestJS 12** (TypeScript 6, ESM) | Модульная архитектура |
| ORM | **Prisma** | Схема = живая документация доменной модели |
| БД | **Supabase Postgres** | Managed Postgres. Доступ к данным приложения — только через backend |
| Файлы | **Supabase Storage** | Приватный бакет + signed URLs, выдаются backend'ом |
| Авторизация | **Supabase Auth** (GoTrue) | Регистрация, вход, подтверждение email, сброс пароля, ротация refresh — на стороне Supabase. Backend валидирует JWT локально по JWKS |
| Real-time | **NestJS WebSocket Gateway (Socket.io)** | Авторизованные сокеты, комнаты по заказу/пользователю |
| Frontend | **Next.js 16 (App Router) + React 19 + Tailwind 4 + shadcn/ui** | Дизайн-система с первого дня |
| Auth SDK | **`@supabase/supabase-js` + `@supabase/ssr`** | Сессия в httpOnly-cookie, автообновление токена |
| Иконки | **lucide-react** | Тот же набор, что в макетах |
| Валидация | **class-validator / class-transformer** | DTO + глобальный ValidationPipe |
| Тесты | **Vitest** (unit + e2e) | Дефолт NestJS CLI. Обязательное покрытие state-машины |
| Линтер | **oxlint** (backend), **ESLint** (frontend) | Дефолты соответствующих CLI |

> **Про авторизацию.** Мы используем Supabase Auth целиком: пароли, сессии, ротация refresh-токенов, подтверждение email, сброс пароля и лимиты на брутфорс — зона ответственности Supabase. Своя реализация всего этого была бы постоянной зоной риска без выигрыша для продукта. Backend не хранит пароли и не выпускает токены; он только **проверяет** пришедший JWT и применяет бизнес-правила.
>
> **Граница ответственности.** Frontend обращается к Supabase напрямую **только** за авторизацией. Все данные приложения — заказы, предложения, файлы, уведомления, профиль — идут исключительно через NestJS API. Прямой доступ браузера к таблицам через Supabase REST запрещён и закрыт технически (§6).

### Структура репозитория

Один репозиторий, npm workspaces. Без Nx и Turborepo — на два приложения это лишняя сложность.

```

frontend/    — Next.js приложение (структура в §7)
shared/      — общие TypeScript-типы и enum (пакет @mybuild/shared)
```

## 3. Доменная модель (Prisma)

### Сущности

- **User** — `id` (UUID, совпадает с `auth.users.id`), `email` (unique), `role` (`CLIENT | COMPANY`), `firstName`, `lastName?`, `phone`, `companyName?`, `city?`, `country?`, `createdAt`, `updatedAt`.
  - Это **профиль**, а не учётная запись. Учётная запись живёт в `auth.users` (управляется Supabase). Связь: `User.id` → `auth.users.id`, внешний ключ с `ON DELETE CASCADE`. Пароли, подтверждение email и сессии в этой таблице не хранятся.
  - Строка профиля создаётся **триггером** на вставку в `auth.users` из `raw_user_meta_data`, которые фронт передаёт в `signUp`. Состояние «учётная запись есть, профиля нет» невозможно.
  - `email` дублируется из `auth.users` для поиска и отображения; синхронизируется тем же триггером при изменении.
  - `companyName` заполняется только для роли `COMPANY` и обязателен для неё — именно он показывается клиенту в списке предложений и в разделе «Подрядчики». Для `CLIENT` поле пустое. Обеспечивается ограничением БД `CHECK (role <> 'COMPANY' OR "companyName" IS NOT NULL)`.
  - `city` / `country` показываются в шапке интерфейса и в карточке подрядчика.

- **Order** — `id`, `orderNumber` (autoincrement, отображается как `ORD-7829`), `clientId` → User, `title`, `category` (`OrderCategory`), `objectType` (`ObjectType`), `description`, `squareMeters` (Float), `verifiedSquareMeters` (Float?), `address`, `clientBudget` (Decimal?), `desiredStartDate` (DateTime?), `price` (Decimal?), `deadline` (DateTime?), `status` (`OrderStatus`), `clientCompletionComment?`, `correctionComment?`, `createdAt`, `updatedAt`.
  - `clientBudget` — **ожидание клиента**, задаётся при создании. `price` — **фактическая цена сделки**, появляется только в момент принятия предложения и равна `proposedPrice` принятого Offer. Это два разных поля, их нельзя смешивать.
  - `deadline` — срок из принятого предложения (`proposedDeadline`), до принятия — `null`.
  - `verifiedSquareMeters` — площадь, уточнённая компанией-исполнителем (см. §4.1).

- **OrderFile** — `id`, `orderId` → Order, `storageKey` (путь в Supabase Storage), `ownerType` (`CLIENT | COMPANY`), `submissionRound` (Int, default 0), `fileHash` (SHA-256, для дедупликации), `originalName`, `mimeType`, `sizeBytes`, `createdAt`.
  - `submissionRound` — номер сдачи работы, к которой относится файл компании (см. §4.1). Для файлов клиента всегда `0`.

- **Offer** — `id`, `orderId` → Order, `companyId` → User, `status` (`OfferStatus`), `comment?`, `proposedPrice` (Decimal), `proposedDeadline` (DateTime), `createdAt`, `updatedAt`. Ограничение: `@@unique([orderId, companyId])` — одна компания подаёт одно предложение на заказ.

- **Notification** — `id`, `userId` → User, `type` (`NotificationType`), `orderId?` → Order, `title`, `body?`, `isRead` (Boolean, default false), `createdAt`. Создаётся при переходах state-машины (см. §8), доставляется по WebSocket и хранится для раздела «Уведомления».

- **Payment**, **UserCard** — вне MVP (см. §11). Схему закладываем интерфейсно, без endpoints.

> Таблицы `RefreshToken` нет: ротацией и ревокацией refresh-токенов занимается Supabase Auth.

### Enum-ы

**OrderCategory** — что именно заказывают. Заменяет прежнюю развилку «создание плана / реализация» на входе в приложение: теперь это просто поле формы создания заказа.

| Значение | Человекочитаемо |
|----------|-----------------|
| `PLAN_CREATION` | Создание плана проекта |
| `PLAN_IMPLEMENTATION` | Реализация плана |

**ObjectType** — что строят/ремонтируют.

| Значение | Человекочитаемо |
|----------|-----------------|
| `APARTMENT` | Квартира |
| `HOUSE` | Частный дом |
| `COMMERCIAL` | Коммерческое помещение |
| `GOVERNMENT` | Гос. объект |

**OrderStatus**

| Значение | Человекочитаемо | Цвет badge |
|----------|-----------------|-----------|
| `WAITING` | Поиск исполнителя | серый |
| `AWAITING_CONFIRMATION` | Ожидает подтверждения (есть предложения, клиент выбирает) | жёлтый |
| `IN_PROGRESS` | В работе | синий |
| `AWAITING_COMPLETION_CONFIRMATION` | Ожидание подтверждения выполнения | жёлтый |
| `COMPLETED` | Завершён | зелёный |
| `COMPLETION_DISPUTED` | На доработке | красный |

**OfferStatus**

| Значение | Человекочитаемо |
|----------|-----------------|
| `SENT` | Предложение отправлено |
| `ACCEPTED` | Предложение принято |
| `REJECTED` | Предложение отклонено |
| `NOT_ACCEPTED` | Не выбрано (другое предложение приняли) |
| `WITHDRAWN` | Предложение отозвано |
| `WORK_SUBMITTED` | Работа сдана, ждёт подтверждения |
| `COMPLETED` | Предложение завершено |
| `BACK_FOR_OVERRIDE` | Возвращено на доработку |

> Имена статусов заказа и предложения не должны совпадать: оба enum встречаются в одной транзакции, и одинаковое имя с разным смыслом — источник ошибок.

**NotificationType** — `OFFER_RECEIVED`, `OFFER_ACCEPTED`, `OFFER_REJECTED`, `WORK_SUBMITTED`, `WORK_CONFIRMED`, `WORK_DISPUTED`, `FILES_UPDATED`, `AREA_VERIFIED`.

> Создание заказа записей `Notification` **не порождает**: новый заказ уходит только broadcast'ом в комнату `company-feed` (§8). Иначе один заказ создавал бы строку в БД на каждую зарегистрированную компанию.

## 4. State-машина заказа (ядро системы)

> Вся логика статусов сосредоточена в одном тестируемом сервисе `OrderStateMachine` с явными разрешёнными переходами. Все переходы выполняются в Prisma-транзакции.

### Переходы Order

| Из | Событие | В | Побочные эффекты |
|----|---------|----|------------------|
| — | клиент создал заказ | `WAITING` | создаётся Order + файлы |
| `WAITING` | компания отправила предложение | `AWAITING_CONFIRMATION` | Offer → `SENT` |
| `AWAITING_CONFIRMATION` | последнее активное предложение отклонено/отозвано | `WAITING` | — |
| `AWAITING_CONFIRMATION` | клиент принял предложение | `IN_PROGRESS` | принятый Offer → `ACCEPTED`; `order.price = offer.proposedPrice`; `order.deadline = offer.proposedDeadline`; все прочие Offer → `NOT_ACCEPTED` |
| `IN_PROGRESS` | компания сдала работу | `AWAITING_COMPLETION_CONFIRMATION` | Offer → `WORK_SUBMITTED` |
| `AWAITING_COMPLETION_CONFIRMATION` | клиент подтвердил | `COMPLETED` | Offer → `COMPLETED` |
| `AWAITING_COMPLETION_CONFIRMATION` | клиент отправил на доработку | `COMPLETION_DISPUTED` | сохраняется `correctionComment`; Offer → `BACK_FOR_OVERRIDE` |
| `COMPLETION_DISPUTED` | компания пересдала работу | `AWAITING_COMPLETION_CONFIRMATION` | Offer → `WORK_SUBMITTED` |

### Правила
- Любой переход, не указанный в таблице, → ошибка `409 Conflict` (`InvalidStateTransition`).
- **Машина реализуется как чистая функция** `(currentStatus, event, context) → { nextStatus, sideEffects[] }` без обращений к БД внутри. Транзакцию открывает и применяет `sideEffects` сервис-обёртка. Так ядро тестируется мгновенно и без базы, а атомарность не страдает.
- Каждый переход выполняется в `prisma.$transaction(...)` — чтобы многошаговые изменения (например, принятие предложения с обновлением остальных) были атомарны и без гонок.
- После успешного перехода эмитится WebSocket-событие и создаётся `Notification` (см. §8).
- Проверка владения: клиент может менять только свои заказы; компания — только заказы со своим Offer.

## 4.1 Детальные бизнес-правила

**Создание заказа**

Поля формы и их обязательность:

| Поле | Обязательно | Примечание |
|------|-------------|-----------|
| `title` — Название заказа | да | напр. «Ремонт квартиры 100м²» |
| `category` — Категория | да | `PLAN_CREATION` / `PLAN_IMPLEMENTATION` |
| `objectType` — Тип объекта | да | квартира / дом / коммерческое / гос. объект |
| `description` — Описание работ | да | |
| `squareMeters` — Площадь (м²) | да | число > 0 |
| `address` — Адрес объекта | да | город, улица, дом (свободная строка) |
| `clientBudget` — Бюджет | нет | ожидание клиента; может не знать заранее |
| `desiredStartDate` — Желаемая дата начала | нет | не раньше сегодняшнего дня |
| файлы | нет | PDF, DWG, изображения; см. лимиты ниже |

- При создании `price` и `deadline` **не задаются** — они появляются только в момент принятия предложения.
- Файлы, загруженные клиентом, получают `ownerType = CLIENT`, `submissionRound = 0`.
- `orderNumber` присваивается автоматически, показывается пользователю как `ORD-{number}`.

**Предложения компаний**
- Компания видит `clientBudget` заказа (если клиент его указал) — это ориентир, а не ограничение: `proposedPrice` может быть любым.
- Предложение содержит: `proposedPrice` (обязательно), `proposedDeadline` — дату завершения работ (обязательно), `comment` (опционально).
- На один заказ может прийти **сколько угодно предложений от разных компаний**, но **одна компания подаёт только одно** (`@@unique([orderId, companyId])`). Повторная отправка **обновляет** существующее предложение, а не создаёт второе (семантика upsert), и возвращает его статус в `SENT`.
- «Доступные для предложений» заказы (`GET /company/orders/available`) = заказы в статусе `WAITING` **или** `AWAITING_CONFIRMATION`, по которым у этой компании **нет предложения ЛИБО её предложение находится в статусе `WITHDRAWN` / `REJECTED`**. Второе условие обязательно: строка Offer остаётся в БД из-за уникального ограничения, и без него компания, отозвавшая предложение, потеряла бы заказ навсегда.
- Клиент видит все активные предложения списком: название компании, цена, срок, комментарий — и выбирает одно. Остальные автоматически получают статус `NOT_ACCEPTED`.

**Уточнение площади компанией**
- Компания-исполнитель (та, чьё предложение принято) может указать `verifiedSquareMeters` — площадь, которую она посчитала фактически, если клиент ошибся при создании заказа.
- Доступно **только** в статусах `IN_PROGRESS`, `AWAITING_COMPLETION_CONFIRMATION`, `COMPLETION_DISPUTED` — то есть после принятия предложения и до завершения.
- Исходное `squareMeters` клиента **не перезаписывается**. В интерфейсе, если `verifiedSquareMeters` задано, показываются оба значения: «указано клиентом» / «уточнено исполнителем».
- Уточнение площади само по себе **не меняет статус заказа и не меняет цену** — это информационное поле.

**Приватность и видимость**
- Компания видит на заказе **только своё** предложение, не предложения конкурентов.
- Компания **не видит** внутренний прогресс заказов, в которых не участвует (в которых у неё нет активного предложения): для неё такой заказ выглядит как `WAITING`.
- Клиент видит список активных предложений (`SENT`), пока заказ в `AWAITING_CONFIRMATION`; после принятия — принятое предложение.
- `correctionComment` (комментарий к доработке) показывается соответствующей стороне в статусах доработки/завершения.

**Файлы и комментарий компании** (`POST /orders/:id/files`)
- При добавлении и комментарий, и хотя бы один файл — **обязательны**.
- Файлы компании **версионируются по сдачам, а не заменяются**. Каждая сдача работы увеличивает `submissionRound` на 1; загруженные файлы получают текущий номер. Прежние файлы **не удаляются** — в сценарии «сдал → клиент отправил на доработку → пересдал» это ровно те файлы, по которым шёл спор.
- В интерфейсе по умолчанию показывается последняя сдача; предыдущие доступны в сворачиваемом блоке «История сдач».
- Дедупликация по SHA-256 действует **в пределах одной сдачи**: файл с уже существующим в этом раунде хешем повторно не сохраняется.

**Удаление заказа**
- Только своим клиентом, и только в безопасных статусах (до начала работ — `WAITING` / `AWAITING_CONFIRMATION`). Заказ в работе или завершённый удалять нельзя.

**Поиск и фильтрация списка заказов**
- Фильтр по статусу (вкладки).
- Поиск строкой по: номеру заказа (`ORD-7829` и просто `7829`), названию заказа, названию подрядчика.
- Пагинация.

## 5. REST API

Чистый ресурсный REST. Все ответы — JSON. Все защищённые маршруты требуют access-токен Supabase (`Authorization: Bearer`) + соответствующую роль.

### Аутентификация

Собственных auth-эндпоинтов у backend'а **нет**. Регистрация, вход, выход, подтверждение email, сброс и смена пароля выполняются фронтендом напрямую через `@supabase/supabase-js`:

| Действие | Как |
|----------|-----|
| Регистрация | `supabase.auth.signUp({ email, password, options: { data: { role, firstName, lastName, phone, companyName, city, country } } })` — метаданные подхватывает триггер, создающий профиль `User` |
| Вход | `supabase.auth.signInWithPassword(...)` |
| Выход | `supabase.auth.signOut()` (`{ scope: 'global' }` — на всех устройствах) |
| Обновление токена | автоматически внутри SDK |
| Подтверждение email | письмо от Supabase → callback-роут в Next.js |
| Сброс пароля | `resetPasswordForEmail` → страница установки нового пароля |
| Смена пароля | `supabase.auth.updateUser({ password })` |

Backend только валидирует пришедший JWT (§6) и отдаёт данные приложения.

### Orders (клиент)
| Метод | Путь | Назначение |
|-------|------|-----------|
| POST | `/orders` | Создать заказ (+ файлы) |
| GET | `/orders?status=&q=&page=` | Свои заказы: фильтр по статусу, поиск, пагинация |

## 6. Безопасность

### Аутентификация (Supabase Auth)
- Пароли, сессии, ротация refresh-токенов с обнаружением повторного использования, подтверждение email, сброс пароля и лимиты на брутфорс — **на стороне Supabase**. Backend паролей не хранит и токенов не выпускает.
- Сессия в Next.js хранится в httpOnly-cookie, которыми управляет `@supabase/ssr`; обновление access-токена — автоматическое.
- Access-токен (JWT, подписан асимметричным ключом проекта) уходит в NestJS в заголовке `Authorization: Bearer`.
- **Backend не ходит в Supabase на каждый запрос:** подпись проверяется локально по JWKS (`/auth/v1/.well-known/jwks.json`) с кэшированием ключей. Проверяются `iss`, `aud`, `exp`.
- **Роль в токене:** Custom Access Token Hook (Postgres-функция) добавляет claim `user_role` из `public.User`. `RolesGuard` читает роль из проверенного JWT без обращения к БД.
- Политика паролей: минимум 8 символов + проверка на утёкшие пароли (настройка проекта Supabase, HIBP).
- Подтверждение email включено: до подтверждения пользователь не может пользоваться кабинетом.

### Модель доступа к данным
- Единственная точка входа к данным приложения — NestJS. Frontend обращается к Supabase напрямую **только** за авторизацией.
- **На всех таблицах схемы `public` включён RLS без единой политики.** Prisma подключается напрямую к Postgres и RLS не подчиняется, а публичный `anon`-ключ, который лежит в браузере, не даёт прочитать ни одной строки через Supabase REST. Это защита на случай, когда ключ утёк или кто-то нашёл его в бандле.
- `service_role`-ключ и строка подключения к БД — **только на backend**, никогда в `NEXT_PUBLIC_*`.
- Storage-бакет приватный; загрузка и выдача signed URL идут через backend, который проверяет участие пользователя в заказе.

### Прочее
- **RBAC:** `@Roles(CLIENT | COMPANY)` + `RolesGuard`.
- **Ownership-guards:** заказ принадлежит запрашивающему клиенту; offer — компании; документ — участнику заказа.
- **CORS:** allowlist origins + `credentials: true`.
- **Helmet**, security-заголовки.
- **Rate limiting:** `@nestjs/throttler` на мутирующих маршрутах (создание заказов, предложений, загрузка файлов). Брутфорс входа закрывает Supabase своими лимитами.
- **Секреты:** только через `@nestjs/config` + `.env`; в репозитории — `.env.example`. Корректный `.gitignore` (`.env`, ключи, локальные БД, локальные загрузки).
- **Валидация загрузок:** MIME/размер; имена файлов санитизируются; бакет приватный.

## 8. Real-time (WebSocket Gateway) и уведомления

### Архитектура
- `OrderGateway` на Socket.io, namespace `/ws`.
- **Авторизация сокета:** при подключении проверяется access-токен Supabase (handshake `auth.token`) — той же проверкой по JWKS, что и REST; неавторизованные отклоняются.
- **Комнаты:**
  - `user:{userId}` — личные уведомления.
  - `order:{orderId}` — все участники конкретного заказа (его клиент + компании с предложением).
  - `company-feed` — компании, подписанные на ленту доступных заказов.

### События (emit при переходах state-машины)
| Событие | Когда | Кому |
|---------|-------|------|
| `order:created` | создан новый заказ со статусом `WAITING` | `company-feed` |
| `order:status_changed` | любой переход статуса | `order:{id}`, `user:{clientId}` |
| `offer:created` / `offer:updated` | компания отправила/изменила предложение | `order:{id}`, `user:{clientId}` |
| `offer:status_changed` | предложение принято/отклонено/отозвано | `order:{id}`, `user:{companyId}` |
| `order:files_updated` | компания добавила файлы/комментарий | `order:{id}`, `user:{clientId}` |
| `order:area_verified` | компания уточнила площадь | `order:{id}`, `user:{clientId}` |
| `notification:created` | создано любое уведомление | `user:{userId}` |

### Связь с уведомлениями
Каждое из этих событий, адресованное конкретному пользователю, **одновременно** создаёт запись `Notification` в БД. Так колокольчик показывает актуальный счётчик в реальном времени, а раздел «Уведомления» — историю, даже если пользователь был офлайн. Создание уведомления происходит в той же транзакции, что и переход статуса.

Исключение — `order:created`: это broadcast в ленту, записей в БД он не создаёт (§3).

Frontend подписывается на нужные комнаты и обновляет состояние без перезагрузки страницы.

## 10. Фазы реализации

- Базовый health-check endpoint, глобальные pipes/filters, helmet/CORS.
- Дизайн-система: Tailwind + shadcn/ui, токены, тема, базовые компоненты (§7).
- Каркас кабинета: боковое меню + шапка (пустые разделы-заглушки).
- Главная страница (лендинг) по §7.
- Типизированный API-клиент + Socket.io-клиент (заглушки).

**DoD:** оба приложения поднимаются; есть подключение к БД; открывается главная страница и каркас кабинета в фирменном дизайне.

### Фаза 1 — Доменная модель и state-машина
- Prisma-схема всех сущностей (§3) + enum-ы, миграции.
- `OrderStateMachine` как чистая функция с явными переходами (§4) + сервис-обёртка, применяющая эффекты в транзакции.
- **Unit-тесты state-машины** (все разрешённые и запрещённые переходы).
- Seed-скрипт: тестовые клиент/компании/заказы во всех статусах.

**DoD:** миграции применяются; тесты переходов зелёные; есть seed-данные.

### Фаза 2 — Аутентификация и доступ
- **Supabase:** включить email/password, подтверждение email, русские шаблоны писем, политику паролей (8+ символов, проверка на утёкшие), лимиты запросов.
- **SMTP:** встроенная почта Supabase имеет жёсткий лимит писем в час и годится только для разработки. Для прода подключается свой провайдер (Resend / Postmark / SES) — настройка в проекте Supabase, кода не требует.
- **Миграция:** `public.User` с `id` = `auth.users.id` (FK, cascade); триггер создания и синхронизации профиля из `raw_user_meta_data`; `CHECK` на `companyName` для роли `COMPANY`; **RLS без политик на всех таблицах `public`**.
- **Custom Access Token Hook:** claim `user_role` в JWT.
- **Backend:** `SupabaseAuthGuard` (валидация подписи по JWKS с кэшем, проверка `iss`/`aud`/`exp`), `@CurrentUser`, `RolesGuard`, `@Roles`. `GET /profile`, `PATCH /profile`.
- **Frontend:** `@supabase/ssr` (клиенты browser/server/proxy), `proxy.ts` — обновление сессии и защита роутов; страницы регистрации (выбор роли, `companyName` обязателен для компании), входа, «забыли пароль», установки нового пароля, callback подтверждения email; редирект client → клиентский кабинет, company → кабинет компании.

**DoD:** регистрация обеими ролями с подтверждением email; вход и выход работают; сброс пароля проходит; профиль создаётся автоматически; защищённый маршрут отдаёт 401 без токена и 403 при чужой роли; по anon-ключу из браузера не читается ни одна таблица.

### Фаза 3 — Заказы клиента (создание, список, детали, файлы)
- Backend: `POST /orders` со всеми полями §4.1 (+ загрузка файлов в Supabase Storage, SHA-256 дедуп), `GET /orders` (статус + поиск + пагинация), `GET /orders/:id`, `DELETE /orders/:id`.
- Модуль `files` (Supabase Storage, signed URLs, валидация загрузок).
- Frontend: список заказов (поиск, вкладки, таблица/карточки, пагинация), форма создания заказа в две колонки, страница деталей.

**DoD:** клиент создаёт заказ со всеми полями и файлами, ищет и фильтрует свои заказы, открывает детали, удаляет заказ.

### Фаза 4 — Предложения компаний и полный цикл сделки
- Backend: `GET /company/orders/available`, `GET /company/offers`, `POST /offers` (цена + срок + комментарий, upsert), `POST /offers/:id/withdraw`, `POST /offers/:id/reject`, `POST /orders/:id/accept-offer/:offerId`, `POST /orders/:id/submit`, `POST /orders/:id/files`, `PATCH /orders/:id/verified-area`, `POST /orders/:id/confirm`, `POST /orders/:id/dispute`. Всё через state-машину и транзакции.
- Frontend: кабинет компании (доступные заказы с бюджетом клиента, форма предложения, мои предложения по статусам, сдача работы с файлами+комментарием, уточнение площади); на клиенте — сравнение предложений, приём/отклонение, подтверждение/доработка, «История сдач».

«Вне MVP» означает: **не подключаем внешнего провайдера и не тратим на это фазу**, но место в системе оставляем готовым — схема БД, точка расширения в коде, заглушка в интерфейсе там, где без неё экран выглядит недоделанным. Продукт должен быть рабочим целиком, а не обрываться на полуслове.

## 12. Архитектурные принципы
1. **Единая state-машина** заказа: все переходы — в одном тестируемом сервисе с явными правилами, никакой логики статусов в контроллерах или при рендере страниц.
2. **Атомарность:** многошаговые изменения (включая создание уведомлений) — в транзакциях, чтобы исключить рассинхрон и гонки.
3. **Безопасность по умолчанию:** аутентификация делегирована Supabase Auth (ротация refresh, подтверждение email, сброс пароля, лимиты входа); backend проверяет JWT локально по JWKS и не хранит паролей; RBAC, RLS без политик как страховка от утечки anon-ключа, throttling, helmet; секреты только в env.
4. **Одна точка входа к данным:** все данные приложения идут через NestJS. Прямой доступ браузера к таблицам Supabase закрыт.
5. **Чистая доменная модель:** один `User` с ролью, понятные имена сущностей (`Order`, `Offer`, `OrderFile`, `Notification`); ожидание клиента (`clientBudget`) и факт сделки (`price`) — разные поля.
6. **Файлы во внешнем хранилище** (Supabase Storage) с signed URLs и дедупликацией по SHA-256.
7. **Сквозная типизация** enum/DTO между backend и frontend.
8. **Дизайн-система с первого дня** вместо ad-hoc стилей.
9. **Тесты на ядро:** state-машина и полный цикл заказа покрыты.
