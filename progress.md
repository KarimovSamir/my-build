# progress.md — журнал подсессий

Рабочий журнал между подсессиями. План подфаз — `PLAN.md`. Правила проекта — `CLAUDE.md`. Требования — `MyBuild_NestJS_TZ.md`.

## Как этим пользоваться

**В начале подсессии агент обязан:**

1. Прочитать этот файл целиком (начиная с последней записи).
2. Посмотреть в `PLAN.md`, какая подфаза идёт следующей.
3. Прочитать раздел ТЗ, к которому относится подфаза.
4. Взять **ровно одну** подфазу. Не больше.

**В конце подсессии агент обязан:**

1. Дописать запись по шаблону ниже — четыре блока, ни один не пропускать.
2. Дать в чат короткий отчёт и указать: «в фазе N осталось: …» либо «фаза N завершена целиком».
3. Остановиться. Не задавать вопрос «делать дальше?». Следующая подфаза — только по явному указанию пользователя.

**Правила для записей:**

- Новая запись добавляется **вниз** файла. Прежние не переписывать и не сокращать.
- «Сделано» пишется только после проверки (`CLAUDE.md` §2). Тесты упали — так и написать, с выводом.
- Незаконченное уходит в «что дальше», а не замалчивается.
- Даты — абсолютные.

## Подфаза 3.1 — модуль `files`: Supabase Storage — 3 сентября 2026

**Сделано**

- **Бакет.** Приватный бакет `order-files` в Supabase (уже существовал, скрипт привёл настройки к нужным: `public: false`, лимит 20 МБ). Заводится командой `npm run storage:setup -w backend` → `backend/scripts/ensure-storage-bucket.ts`, идемпотентна. Упомянута в `backend/env.example`.
- **`src/supabase/supabase.module.ts`** — клиент Supabase с секретным ключом как провайдер Nest (токен `SUPABASE_ADMIN`). Не глобальный: импортирует только тот, кому он нужен. Seed и e2e по-прежнему берут клиент напрямую из `supabase-admin.ts` — там контейнера DI нет.
- **`src/modules/files/file-validation.ts`** — чистые функции: `prepareFile` (размер по содержимому, 400 на пустой, 413 на >20 МБ, SHA-256), `resolveMimeType`, `sanitizeFileName` (транслит кириллицы, отрезание пути, схлопывание символов, ограничение длины).
- **`src/modules/files/storage.service.ts`** — обёртка над бакетом: `upload` (с `upsert`, потому что в ключе лежит хеш содержимого), `createSignedUrl` (TTL 300 с, `download` → Content-Disposition), `remove` (ошибку не бросает, пишет в лог).
- **`src/modules/files/files.service.ts`** — `attachFiles` (валидация → дедуп внутри пачки и внутри сдачи → загрузка → `createManyAndReturn` со `skipDuplicates` → уборка объектов, чьи строки не создались), `getDownloadUrl`, `listOrderFiles`, `assertOrderParticipant`, `removeStorageObjectsForOrder`. Ключ объекта: `orders/{orderId}/{client|company}/{round}/{хеш16}-{имя}`.
- **`FilesModule`** подключён в `app.module.ts`. Своих маршрутов нет: загрузка живёт на маршрутах заказа (3.2 и 4.2), раздел «Документы» переиспользует сервис в 6.1.
- **Проверено:** 123 unit-теста (было 92; новые — `file-validation.spec.ts` и `files.service.spec.ts`), 27 e2e (было 18; новый `test/files.e2e-spec.ts` — 9 тестов на живом Supabase), `npm run typecheck`, `npm run lint`, `npm run build` всего репозитория — всё зелёное.
- **Ручная проверка вне тестов** (временный скрипт, удалён): настоящий PNG 15 320 байт → строка `OrderFile` создана → объект виден в бакете тем же размером → signed URL отдал 200 и побайтово те же данные → `removeStorageObjectsForOrder` очистил папку. Бакет после всех прогонов пуст.

**Принятые решения**

- **Тип файла определяется расширением, а не заголовком запроса.** Браузер для DWG почти всегда шлёт `application/octet-stream` — по строгому allowlist'у DWG нельзя было бы загрузить вовсе, хотя ТЗ §5 его требует. Поэтому: расширение обязано быть в таблице, а заявленный MIME либо совпадает с ним (с учётом синонимов вроде `application/acad`), либо не распознан клиентом. Подмена (`.exe` под видом PDF) отсекается расширением, `.pdf` с чужим типом — сверкой. В базу пишется канонический тип, а не то, что назвал клиент.
- **Доступ к файлам: клиент заказа либо компания-исполнитель.** Список статусов предложения свой — `ACCEPTED / WORK_SUBMITTED / BACK_FOR_OVERRIDE / COMPLETED`; он отличается от `EXECUTING_OFFER_STATUSES` в `OrderTransitionService` добавленным `COMPLETED`: после сдачи компания должна сохранять доступ к тому, что сама загружала. Компания со статусом `SENT` файлов не видит (ТЗ §4.1: приватность).
- **Проверка по идентификатору, а не по роли.** Роль в токене живёт час и может устареть, связь с заказом — нет.
- **Из одинаковых файлов в пачке остаётся первый**, а не последний: пользователь видит то имя, под которым приложил файл.
- **Имя для скачивания транслитерируется, если в нём не только ASCII** (`toDownloadName`). Причина — в граблях ниже. Настоящее имя не теряется: оно в `OrderFile.originalName` и показывается в интерфейсе.
- **`UploadedFileInput` — своя форма, не multer'овская.** Сервис не зависит от транспорта, и unit-тесты не поднимают Express.
- **Уборка бакета — отдельный метод, а не каскад.** Строки `OrderFile` уходят каскадом за заказом, объекты в хранилище — нет; 3.2 обязана вызвать `removeStorageObjectsForOrder` перед удалением заказа.

**Что дальше**

- Подфаза **3.2** — backend `orders`: CRUD (`POST /orders` multipart, `GET /orders`, `GET /orders/:id`, `DELETE /orders/:id`, `OwnershipGuard`, throttler).
- Незакрытого из 3.1 нет. Маршрутов у модуля files нет намеренно — они появятся вместе с заказами.

**Где грабли**

- **Supabase ломает кириллицу в имени скачиваемого файла.** Параметр `download` он не декодирует, а в Content-Disposition подставляет как есть: имя доезжает percent-кодированным дважды (`Логотип.png` → `%D0%9B%D0%BE…`). Обойти со стороны клиента нельзя — `fetch` и браузер кодируют значение в URL сами. Поэтому не-ASCII имена уходят транслитерированными. Если Supabase починит — снять `toDownloadName` в `files.service.ts`.
- **Multer портит UTF-8 в `originalname`.** Express-multer читает имя из multipart как latin1. В 3.2 на границе контроллера имя нужно чинить: `Buffer.from(file.originalname, 'latin1').toString('utf8')`, иначе в базу попадут «ÐÐ»Ð°Ð½.pdf». Проверить это тестом на настоящей загрузке через HTTP.
- **Скрипты на `tsx` не могут поднять Nest.** `tsx` (esbuild) не умеет `emitDecoratorMetadata`, поэтому `NestFactory.create*(AppModule)` падает уже на валидации `.env` (`PORT must be an integer`: без метаданных class-transformer не преобразует строку в число). В скриптах сервисы собираются руками, как в seed. Отдельно: при `{ logger: false }` Nest съедает эту ошибку и процесс молча выходит с кодом 1 — отлаживать только с включённым логгером.
- **Бакет не создаётся сам.** На свежем проекте Supabase перед первой загрузкой нужен `npm run storage:setup -w backend` — как миграции для базы.
- **Файлы seed по-прежнему существуют только в БД** (грабли Фазы 1 в силе): у их строк `OrderFile` нет объектов в бакете, поэтому `getDownloadUrl` на seed-данных вернёт ссылку, по которой ничего не скачается. Чинить в seed не стали: это работа не 3.1, а того момента, когда seed начнёт грузить настоящие файлы.
- **Дедупликация не защищает от гонки полностью.** Два одновременных запроса с одним файлом ловятся уникальным ограничением базы (`orderId + submissionRound + fileHash`), `skipDuplicates` не даёт запросу упасть, а лишний объект убирается по разнице ключей.

## Подфаза 3.2 — backend `orders`: CRUD — 3 сентября 2026

**Сделано**

- **Маршруты** (`src/modules/orders/orders.controller.ts`), все четыре из ТЗ §5:
  - `POST /orders` — multipart с файлами, роль `CLIENT`, статус `WAITING`, файлы получают `ownerType = CLIENT` и `submissionRound = 0`. Ограничение частоты: 20 запросов в минуту.
  - `GET /orders?status=&q=&page=&pageSize=` — свои заказы, фильтр по статусу, поиск, пагинация, роль `CLIENT`.
  - `GET /orders/:id` — обе роли, ответ ролезависимый.
  - `DELETE /orders/:id` — роль `CLIENT`, только свой заказ и только в `WAITING` / `AWAITING_CONFIRMATION`, ответ 204. Ограничение: 30 в минуту.
- **`OwnershipGuard`** (`src/common/guards/ownership.guard.ts`) — первое применение, ТЗ §9. Режим задаётся декоратором `@OrderAccess(OWNER | VIEWER)`; найденный заказ кладётся в запрос и достаётся в контроллере через `@OrderAccessCtx()`, чтобы сервис не повторял тот же запрос к базе.
- **`ThrottleGuard`** (`src/common/guards/throttle.guard.ts`) + `@Throttle({ limit, ttl })` — своя реализация вместо `@nestjs/throttler` (причина ниже, решение принял пользователь). Скользящее окно в памяти по «пользователь + маршрут», 429 с `Retry-After`.
- **`order-view.ts`** — чистые функции `toOrderListItem` / `toOrderDetail` / `resolveVisibility`: вся приватность ТЗ §4.1 в одном месте, без базы и без Nest.
- **`order-participation.ts`** — `EXECUTOR_OFFER_STATUSES` и `ACTIVE_OFFER_STATUSES`. `FilesService` теперь берёт список оттуда же, а не держит свою копию.
- **`OrdersService`** — создание с откатом заказа при отказе на файлах, список с поиском (`buildSearchConditions`), детали, удаление с уборкой бакета.
- **DTO** — `CreateOrderDto` и `ListOrdersQueryDto` с русскими сообщениями валидации, зеркало для формы Фазы 3.4.
- **`FilesService`** — добавлены `listStorageKeys` и `removeStorageObjects`; `removeStorageObjectsForOrder` теперь через них. Нужно для правильного порядка удаления заказа.
- **Проверено:** 148 unit-тестов (было 123; новые — `order-view.spec.ts` на приватность и `throttle.guard.spec.ts`), 59 e2e (было 27; новый `test/orders.e2e-spec.ts` — 32 теста на живой Supabase), `npm run typecheck`, `npm run lint`, `npm run build` всего репозитория — всё зелёное.
- **Ручная проверка вне тестов:** собранный backend (`node dist/main.js`) поднят, `/health` отдал `database: "up"`, все четыре маршрута смонтированы и без токена отдают 401. С настоящими токенами seed-пользователей проверены на живых данных: список с пагинацией (`total: 6`), поиск `ORD-24`, поиск по подрядчику «СтройГрад» (2 заказа), детали глазами клиента и глазами компании-исполнителя, 403 на `GET /orders` от компании.

**Принятые решения**

- **`@nestjs/throttler` не поставлен — написан свой guard. Решение пользователя от 3 сентября 2026.** Последняя версия библиотеки (6.5.0) объявляет peer-зависимость только до NestJS 11, а в проекте 12; `overrides` в npm на peer-конфликты не действуют, оставался только репозиторный `legacy-peer-deps`, который отключил бы проверку совместимости во всём репозитории. Свой guard — ~110 строк, покрыт unit-тестами, без зависимости. В Фазе 7.3 при желании меняется на библиотеку правкой одного модуля.
- **Чужой заказ отдаётся как 404, а не 403** — и на `GET`, и на `DELETE`. В `PLAN.md` для 3.2 было написано «403 на чужой заказ», но 403 подтверждает существование заказа с таким идентификатором. 403 в наборе остался там, где он честен: чужая роль (компания на маршрутах клиента). Подфаза 3.5 требует 404 на странице деталей — это тот же выбор.
- **Компания видит любой заказ, но без прогресса.** ТЗ §4.1 сформулировано как «для неё такой заказ выглядит как `WAITING`», то есть заказ видим, а урезан состав: статус подменяется на `WAITING`, цена, срок, подрядчик, уточнённая площадь, комментарии, файлы и чужие предложения не отдаются. Задание клиента (описание, адрес, площадь, бюджет) остаётся видимым — по нему компания и подаёт предложение.
- **Активное предложение = `SENT` + статусы исполнителя.** Компания с `SENT` видит настоящий статус заказа, но не файлы: файлы даются только исполнителю, как в `FilesService` из 3.1. Компания с `WITHDRAWN` / `REJECTED` / `NOT_ACCEPTED` видит заказ как посторонняя, но своё выбывшее предложение — по-прежнему видит.
- **Клиенту показываются только предложения, которые ещё в игре** (`SENT` + статусы исполнителя). Отозванные, отклонённые и невыбранные ему уже ни на что не влияют (ТЗ §4.1).
- **Порядок при создании: сначала строка заказа, потом файлы, при отказе — откат.** Ключ объекта в хранилище содержит `orderId`, поэтому иначе не выходит. Побочный эффект: номера заказов идут с пропусками — для autoincrement нормально и пользователю не видно.
- **Порядок при удалении: ключи → удаление строки → уборка бакета.** Строки `OrderFile` уходят каскадом, и после удаления узнать, что убирать из хранилища, уже неоткуда.
- **`ThrottleGuard` на `DELETE` идёт перед `OwnershipGuard`** — ограничитель дешевле похода в базу и заодно тормозит перебор идентификаторов.

**Где грабли**

- **`enableImplicitConversion` ломает необязательные поля типа `Date`.** Глобальный `ValidationPipe` преобразует значение по объявленному типу поля *до* собственных `@Transform`. Пустая строка из multipart (браузер шлёт незаполненные поля именно так) превращалась в `Invalid Date`, и своё преобразование получало уже её, а не `''`. Поэтому `desiredStartDate` объявлен как `string` с `@IsDateString` и своим валидатором `IsNotPastDate`, а в `Date` его превращает сервис. Для любого нового необязательного поля-даты — так же.
- **`defParamCharset: 'utf8'` в `FilesInterceptor` обязателен.** По умолчанию multer читает имена файлов из multipart как latin1. Это те самые грабли из 3.1 — чинить `Buffer.from(name, 'latin1')` вручную не понадобилось, опция решает вопрос на входе. Проверено e2e: «План квартиры.pdf» доезжает целым.
- **`@types/multer` не ставили.** В контроллере объявлен свой интерфейс на три поля. Если понадобится больше — не тянуть пакет ради типа, а дописать интерфейс.
- **Порядок сортировки в тестах не проверить на параллельно созданных заказах.** `Promise.all` из трёх `prisma.order.create` даёт непредсказуемый порядок `createdAt`, и тест на «новые сверху» падал через раз. В `orders.e2e-spec.ts` фикстуры создаются строго по очереди.
- **e2e на ограничитель частоты берёт отдельного пользователя.** Тест выбирает лимит `POST /orders` целиком, и на общем пользователе он сломал бы остальные тесты файла. Окно живёт в памяти приложения, между файлами e2e не переносится (приложение поднимается заново), но внутри файла — переносится.
- **Прогон e2e вырос до ~36 секунд** (было ~14): добавились 32 теста, ходящих в реальную Supabase. Таймаутов в `vitest.config.e2e.ts` (60 с) хватает с запасом.

## Подфаза 3.2 — доработка по итогам ревизии — 3 сентября 2026

Пользователь спросил, осталась ли в 3.2 явная проблема. При целенаправленной проверке нашлась одна настоящая — исправлена, плюс подчищено одно место, которое маскировало ошибки.

**Сделано**

- **Исправлено: поиск по длинной строке цифр отдавал 500.** `Order.orderNumber` — колонка `Int` (32 разряда), а `parseOrderNumber` пропускал любое безопасное целое. Запрос `?q=99999999999` доходил до базы и падал там с `PrismaClientKnownRequestError: value out of range for type integer`, который `AllExceptionsFilter` превращал в 500 «Внутренняя ошибка сервера». Воспроизведено на живой базе до правки.
  - В `shared/src/labels.ts` добавлена константа `MAX_ORDER_NUMBER = 2_147_483_647`, и `parseOrderNumber` теперь возвращает `null` для всего, что вне диапазона `1…MAX_ORDER_NUMBER`. Правка именно в `shared/`: тем же разбором в 3.3 будет пользоваться поиск на фронте, и расходиться им нельзя.
  - Построение условий поиска вынесено из `orders.service.ts` в чистый модуль `src/modules/orders/order-search.ts` — чтобы правило проверялось unit-тестом, а не только прогоном по живым данным.
- **Убрано маскирование ошибки при откате создания заказа.** Если загрузка файлов отклонена, заказ удаляется; раньше отказ самого удаления затирал исходную причину, и понятный 400 «такой тип загрузить нельзя» превращался бы в 500. Теперь откат best-effort с записью в лог, наружу уходит исходная ошибка.
- **Проверено:** 155 unit-тестов (было 148; новый `order-search.spec.ts` — 7 тестов), 60 e2e (было 59; новый тест на длинную строку цифр в поиске), типы, линтер и сборка всего репозитория.

**Отдельно проверено и оказалось в порядке**

- Пагинация переполнением не ломается: `skip` уходит в `OFFSET` как 64-разрядное, `page=1e15` отрабатывает без ошибки.
- Отрицательная площадь, неизвестная категория, пустые необязательные поля, дата в прошлом, файл чужого типа — всё отсекается валидацией и покрыто e2e.

**Что дальше**

- Подфаза **3.3** — frontend: список заказов. План не изменился.
- Незакрытого из 3.2 нет.

**Где грабли**

- **Любое число из пользовательского ввода, которое идёт в колонку `Int`, надо ограничивать до похода в базу.** Prisma не приводит его к диапазону и не даёт внятной ошибки — запрос падает в Postgres, а наружу уходит 500. В Фазах 4–6 это касается всего, что будет искать по номерам.

**Принятые решения**

- **Список рендерится на сервере, а не в браузере.** `PLAN.md` предлагал начать 3.3 с браузерного API-клиента, но для этого экрана он не нужен: фильтр живёт в адресе, данные приходят вместе со страницей, ссылку на выборку можно переслать, а кнопка «назад» возвращает предыдущий фильтр. Браузерный клиент появится в 3.4, где он нужен по-настоящему — форма создания заказа грузит файлы multipart прямо из браузера. Заводить его сейчас значило бы положить в репозиторий модуль без единого вызывающего.
- **Живое обновление Фазы 5 это не ломает:** по событию сокета делается `router.refresh()`, и серверный компонент перезапрашивает список без перезагрузки страницы.
- **Вкладок семь: «Все» и шесть статусов**, а не три, как на макете. API принимает ровно один статус, группировки («В работе», «Завершённые») там нет, а ТЗ §4.1 требует фильтр по статусу. Макет ниже ТЗ по приоритету.
- **В колонке «Бюджет» всегда подписано, какое из двух чисел показано.** ТЗ §3 запрещает смешивать `clientBudget` (ожидание клиента) и `price` (цена сделки). Показывается `price`, если он есть, иначе `clientBudget`, и под суммой мелким шрифтом — «цена сделки» или «бюджет клиента».
- **Колонка «Срок» — это `deadline` из принятого предложения**, поэтому до принятия там прочерк. Желаемой даты начала в `OrderListItem` нет, и добавлять её значило бы менять контракт API — это вопрос к пользователю, а не решение подфазы.
- **Кликается вся строка**: `<tr>` получает `position: relative`, а ссылка в первой ячейке растягивается на строку (`after:absolute after:inset-0`). Вкладывать `<a>` вокруг `<tr>` нельзя. Если бы приём не сработал, деградация мягкая — ссылка на названии заказа остаётся рабочей.
- **Отдельного `loading.tsx` нет.** Скелет даёт `<Suspense>` вокруг списка: так шапка с поиском остаётся на экране, а `loading.tsx` подменял бы страницу целиком и на каждой букве отбирал бы фокус у поля.

**Принятые решения**

- **Общие правила формы уехали в `shared/`, а не продублировались.** `CLAUDE.md` §5 запрещает дублировать типы и enum руками, и те же грабли здесь: разъехавшись, форма и DTO дали бы либо ложную ошибку, либо 400 после отправки. Заодно `EXTENSION_MIME` из `file-validation.ts` стал `FILE_EXTENSION_MIME` в `shared/` — по нему фронт отбирает файлы в диалоге и отсеивает лишние.
- **Дата сравнивается по UTC и на фронте, и на бэке.** `CreateOrderDto` считает «сегодня» по UTC; календарь запрещает дни раньше того же UTC-сегодня. Иначе западнее Гринвича форма предлагала бы день, который сервер отклонит.
- **Своя валидация на `useState`, без react-hook-form и zod.** Формы авторизации написаны так же, набор правил маленький, а новая зависимость ради одной формы — лишний вес и лишний повод для конфликта версий.
- **Отправка из браузера, а не серверным действием.** Файлы уходят в API напрямую; server action заставил бы гнать те же 20 МБ сначала в процесс Next.js, а потом в NestJS.
- **Ошибки API показываются списком над кнопкой, а не под полями.** Сообщения валидации приходят строками без имени поля — привязать их к полю нечем. Под полями показывается то, что форма нашла сама до отправки.
- **Запятая в числах принимается** (`62,5` → `62.5`): для русского интерфейса это привычный разделитель, а backend ждёт точку.
- **«Отмена» — ссылка на `/orders`, а не `router.back()`.** На форму приходят и по прямому адресу, и тогда «назад» уводит неизвестно куда.
- **Подпись «Файлы» связана с кнопкой dropzone** (`label htmlFor` → `button id`), скрытому `input[type=file]` дано имя, адресу — `autocomplete="street-address"`. Без этого Chrome писал в консоль замечания к разметке формы.

**Где грабли**

- **`next start` не переживает пересборку.** Оставшийся с прошлой подсессии `next start` после `npm run build` начал отдавать HTML со ссылками на исчезнувшие чанки: страница грузилась, но не гидратировалась, и форма входа отправлялась как обычный GET. Выглядит как ошибка в коде, а на деле — устаревший сервер. После каждой сборки процесс перезапускать. Оба сервера проверки (`node dist/main.js` и `next start -p 3000`) остаются запущенными после этой подсессии.
- **Radix Select внутри `<form>` рендерит скрытое поле.** Без пропа `name` у него нет имени, и Chrome ругается в консоли. Для каждого нового Select в форме — задавать `name`.
- **`Set-Content -Encoding utf8` в Windows PowerShell 5.1 дописывает BOM.** Правка импортов в четырёх файлах превратилась в изменение первой строки каждого. Массовые замены делать через `[System.IO.File]::WriteAllText` с `UTF8Encoding($false)` — или обычным Edit.
- **Файлы `.env` агенту читать нельзя** (запрет доступа), поэтому значения окружения проверяются только косвенно — через `env.example` и поведение приложения.
- **Ограничение в 10 файлов — на запрос, а не на заказ.** Константа называется `MAX_FILES_PER_REQUEST`, и в Фазе 4 компания сможет добавить ещё столько же в своей сдаче. Если понадобится потолок на заказ целиком — это отдельная проверка в `FilesService`, её сейчас нет.
