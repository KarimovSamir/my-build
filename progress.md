## Как этим пользоваться

**В начале подсессии:**

1. Прочитать этот файл целиком — здесь только текущая фаза, это быстро.
2. Посмотреть в `PLAN.md`, какая подфаза идёт следующей.
3. Прочитать раздел ТЗ, к которому она относится.
4. Взять **ровно одну** подфазу. Не больше.

**В конце подсессии:**

1. Дописать запись по шаблону ниже — четыре блока, ни один не пропускать.
2. Дать в чат короткий отчёт и указать: «в фазе N осталось: …» либо «фаза N завершена целиком».
3. Остановиться. Не спрашивать «делать дальше?».

**Правила для записей:**

- Новая запись добавляется **вниз**. Прежние записи этой фазы не переписывать.
- «Сделано» пишется только после проверки (`CLAUDE.md` §2). Тесты упали — так и написать, с выводом.
- Незаконченное уходит в «что дальше», а не замалчивается.
- Пишем состояние, а не историю: «сейчас работает так», а не «было А, стало Б».
- Без дат, без времени прогона тестов и без точных чисел тестов: всё это устаревает к следующей подсессии и врёт следующему агенту.

**Когда фаза закрыта целиком** (`CLAUDE.md` §9): свернуть записи в `CLAUDE.md` §6 (3–6 строк о том, что теперь есть), отступления — в §7, долгоживущие грабли — в §10, и **очистить этот файл** до шапки, шаблона и точки входа в следующую фазу. Летопись живёт в git, не здесь.

## Подфаза 6.1 — Backend: `/contractors` и `/documents`

**Сделано**

- **Каталог подрядчиков.** `ContractorsController` (`modules/users/`, `@Roles(CLIENT)`, `ThrottleGuard` 60/мин): `GET /contractors?q=&page=` и `GET /contractors/:id`. Отбор — в чистом `contractor-search.ts` (`role = COMPANY`, `companyName IS NOT NULL`; поиск по названию **и городу**, с экранированием LIKE). `ContractorsService` считает `completedOrdersCount` одним запросом через `_count` с фильтром по предложениям в статусе `COMPLETED`. Порядок — алфавитный, `id` вторым ключом. Карточка ищется условием каталога целиком, поэтому профиль клиента по этому адресу не читается: 404.
- **Документы.** `GET /documents?ownerType=&orderId=&page=` лёг на прежний `DocumentsController` рядом со скачиванием. Область видимости — в чистом `document-scope.ts`, сервис — `documents.service.ts`, DTO — `dto/list-documents.dto.ts` (`ownerType` через `@IsEnum`, `orderId` через `@IsUUID` — мусор даёт 400, а не 500 из Postgres). Порядок: новые сверху, `id` вторым ключом.
- **Мапинг строки файла вынесен** из `files.service.ts` в `file-view.ts` (`toOrderFileDto`, `toDocumentListItem`) — теперь мест два, и копия разъехалась бы молча.
- **`shared/`:** новый `DocumentListItem` (файл + `orderNumber` + `orderTitle`), `ContractorCard` был описан заранее и не менялся.
- **Чем проверено.** `npm run typecheck`, `npm run lint`, `npm test` (все три пакета) — зелёные. Новые unit-наборы: `document-scope.spec.ts`, `contractor-search.spec.ts`. Новые e2e: `contractors.e2e-spec.ts`, `documents.e2e-spec.ts` (22 теста). Полный `npm run test:e2e` — 11 файлов, всё зелёное. Оба раздела дёрнуты на живом сервере под seed-аккаунтами: каталог отдаёт три компании с `completedOrdersCount: 1` у «СтройГрада», компании — 403; документы клиента — 12 строк, той же компании — 4, `?orderId=нет` — 400.

**Принятые решения**

- **Что попадает в «Документы» компании** → только заказы, где её предложение принято (`EXECUTOR_OFFER_STATUSES`, включая `COMPLETED`). Заказы, по которым она лишь подала предложение, в список не идут, хотя задание клиента там скачать может (`companySeesTaskFiles`): раздел — про свои файлы по своим заказам, а набор иначе менялся бы сам собой, когда клиент выбирает другого исполнителя. Список строго уже прав на скачивание, то есть показанное всегда скачивается.
- **Роль в условии видимости документов не спрашивается вовсе** → `OR` из «я клиент заказа» и «я исполнитель заказа». Клиент не бывает автором предложения, компания не бывает владельцем заказа, поэтому условие точно для обеих ролей; право даёт связь с заказом, а не claim, который живёт час.
- **Поиск в каталоге идёт и по городу** → карточка показывает именно название и город (ТЗ §7), а «найти подрядчика в своём городе» — первое, зачем каталог открывают. ТЗ говорит просто `?q=`, так что это уточнение, а не расхождение.
- **«Кем загружен» — это `ownerType`, без имени** → у заказа обе стороны известны из самого заказа, а колонки `uploadedById` нет намеренно (`CLAUDE.md` §7).
- **Один тип `ContractorCard` и на список, и на карточку** → состав полей у них совпадает; два описания одного и того же завели бы второй источник правды.

**Что дальше**

- Следующая подфаза по `PLAN.md` — **6.2**: frontend `/contractors` (список с поиском и карточка компании). Список строится на общих `lib/list-params.ts`, `components/list-parts.tsx`, `list-search.tsx` — он пятый по счёту, отдельной механики не заводить.
- Незакрытого в 6.1 нет.

**Где грабли**

- **`_count` из Prisma нельзя читать точкой** — oxlint (`no-underscore-dangle`) даёт предупреждение на `row._count`, но не на деструктуризацию. Отсюда `function toContractorCard({ _count, ...row })`; так же устроено чтение `_sum` в `files.service.ts`.
- **`ContractorCard.companyName` — `string`, а колонка `text?`.** Обязательность держит CHECK-ограничение (ТЗ §3) и условие `companyName: { not: null }` в выборке; типам Prisma об этом неоткуда знать, поэтому в мапинге стоит `!`. Убрать условие из `buildContractorsWhere` — значит превратить утверждение в ложь.
- **Каталог общий на всю базу.** e2e не может проверять длину списка: соседние наборы и seed тоже заводят компании. `contractors.e2e-spec.ts` метит свои фикстуры случайной строкой в названии и ищет по ней.
- **Сортировка документов обязана иметь второй ключ.** `createdAt` у файлов одной загрузки совпадает до миллисекунды (`DEFAULT CURRENT_TIMESTAMP` — время начала транзакции), и в постраничном списке без `id` строка способна пропасть со второй страницы, потому что уехала на первую. Видно прямо на seed: у всех файлов одной сдачи одинаковый `createdAt`.
- **`GET /contractors/:id` не разбирает `:id` через `ParseUUIDPipe`.** Проверка живёт в сервисе (`isUuid`), потому что маршрут обязан отвечать 404 на любой мусор, а не 400: «такой компании нет» — честный ответ и для чужого клиента, и для битого идентификатора.

- **Название компании не подставляется в `<title>`** → это стоило бы второго запроса к API за теми же данными. Так же сделана страница заказа.
- **`initialOf` стал общим и пропускает правовую форму** → правка задевает и карточку пользователя в боковом меню (компания видит там теперь букву названия, а не «О»). Дублировать функцию с разными правилами в двух местах было бы хуже.

- **Фильтр «Заказ»** — `components/documents/order-filter.tsx` (серверный, под своим `<Suspense>`) плюс клиентский `order-select.tsx`. Варианты берутся из источника роли: у клиента — `GET /orders`, у компании — `GET /company/offers`, отфильтрованные `isExecutorOffer`, то есть ровно те заказы, где у неё могут быть документы. Оба фильтра сохраняются друг при друге и живут в адресе.
- **Живое обновление** — `DOCUMENTS_EVENTS` в `lib/live-updates.ts`: одно событие `order:files_updated`.
- **`readUuidParam` в `lib/list-params.ts`** — общий разбор идентификатора в адресе; `breadcrumbs.ts` перешёл на тот же `UUID_PATTERN` вместо своей копии регулярки.
- **Чем проверено.** `npm run typecheck`, `npm run lint`, `npm test` (все три пакета) — зелёные; `npm run build -w frontend` собирается. Новые unit-наборы: `documents-filter.spec.ts`, `document-view.spec.ts`, дополнен `live-updates.spec.ts`. В браузере, двумя окнами с разными сессиями: у клиента 12 строк и 6 заказов в фильтре, у компании 4 строки и 2 заказа, подписи «Ваш файл»/«Файл клиента» на одном и том же файле разные; сочетание вкладки и заказа даёт «Показано 1 из 1», пустая выборка — «Ничего не найдено» со сбросом, `?ownerType=SOMEBODY&orderId=not-a-uuid&page=7` — список без фильтров и «На этой странице документов нет»; компания загрузила файл в сдачу ORD-2024 — строка появилась у клиента в открытом `/documents` без перезагрузки (`navigation.length` остался 1), и она же скачалась настоящим файлом из бакета. Проверены обе темы и эмуляция 390×844; в консоли — только известное предупреждение `next/image` (7.2). База возвращена `npm run db:seed`.

**Принятые решения**

- **Своего маршрута «мои заказы» для фильтра заводить не стали** → варианты берутся из уже существующих `GET /orders` и `GET /company/offers`. Новый маршрут API ради выпадающего списка — это контракт, который потом придётся поддерживать, а правило видимости у него было бы третьей копией `buildDocumentsWhere`.
- **Список вариантов ограничен одной страницей `MAX_PAGE_SIZE`** → фильтр это удобство, а не право доступа. Заказ, не попавший в сотню, всё равно фильтруется через адрес: `withSelectedOrder` добавляет выбранный заказ в список под нейтральной подписью, иначе поле выглядело бы пустым при действующем фильтре.
- **Поиска по имени файла нет** → `GET /documents` его не принимает (ТЗ §5), а искать на фронте внутри одной страницы выдачи — обманывать пользователя: файл со второй страницы «не найдётся».
- **Подписи владельца ролезависимые** → «Мои файлы» вместо «Файлы клиента» у клиента. Роль для этого и так есть в рендере (`getCurrentUser` закэширован на запрос, layout зовёт его же), а нейтральные подписи заставляли бы каждый раз вспоминать, кто здесь кто.
- **Живьём раздел слушает одно событие** → `order:files_updated`. Оно приходит клиенту в личную комнату, то есть догоняет ровно тот случай, когда список меняется чужими руками. Файлы задания клиент прикладывает один раз при создании заказа, а своей вкладке событие о своём же действии не адресуется (`CLAUDE.md` §10).
- **`UUID_PATTERN` вынесен в `list-params.ts`** → вторая копия той же регулярки в `breadcrumbs.ts` разъехалась бы молча.

**Где грабли**

- **Ручная проверка загрузки оставляет в бакете осиротевший объект.** `npm run db:seed` чистит только базу: строки `OrderFile` исчезают, объект в Supabase Storage остаётся навсегда. На поведение это не влияет (ссылок на него нет), но «в бакете пусто» после seed — уже неправда.
- **Radix Select не принимает пустую строку значением пункта.** «Все заказы» поэтому имеет свой ключ `all`, который при сборке адреса превращается в отсутствие параметра. Пункт с `value=""` роняет компонент в рантайме, а не на типах.
- **Список вариантов фильтра и список документов — два независимых запроса.** Заказ может быть в фильтре и не иметь ни одного файла (у клиента так выглядит любой заказ без вложений): пустой ответ на такой выбор — норма, а не расхождение.
- **Эмуляция `colorScheme: "dark"` в Chrome тёмную тему здесь не включает.** Тема хранится `next-themes` в `localStorage` и по умолчанию стоит явным `light`, то есть `prefers-color-scheme` не спрашивают вовсе. Проверять — переключателем в шапке или подменой `localStorage.theme` с перезагрузкой.
