# progress.md — журнал текущей фазы

Рабочий журнал между подсессиями **одной фазы**. Правила проекта, состояние кода и грабли — `CLAUDE.md`. План подфаз — `PLAN.md`. Требования — `MyBuild_NestJS_TZ.md`.

---

## Как этим пользоваться

**В начале подсессии:**

1. Прочитать этот файл целиком — здесь только текущая фаза, это быстро.
2. Посмотреть в `PLAN.md`, какая подфаза идёт следующей.
3. Прочитать раздел ТЗ, к которому она относится.
4. Взять **ровно одну** подфазу. Не больше.

**В конце подсессии:**

1. Дописать запись по шаблону ниже — четыре блока, ни один не пропускать.
2. Дать в чат короткий отчёт и указать: «в фазе N осталось: …» либо «фаза N завершена целиком».
3. Остановиться. Не спрашивать «делать дальше?».

**Правила для записей:**

- Новая запись добавляется **вниз**. Прежние записи этой фазы не переписывать.
- «Сделано» пишется только после проверки (`CLAUDE.md` §2). Тесты упали — так и написать, с выводом.
- Незаконченное уходит в «что дальше», а не замалчивается.
- Даты — абсолютные.
- Пишем состояние, а не историю: «сейчас работает так», а не «было А, стало Б».

**Когда фаза закрыта целиком** (`CLAUDE.md` §9): свернуть записи в `CLAUDE.md` §6 (3–6 строк о том, что теперь есть), отступления — в §7, долгоживущие грабли — в §10, и **очистить этот файл** до шапки, шаблона и точки входа в следующую фазу. Летопись живёт в git, не здесь.

## Разбор аудита Фазы 4: средние находки — 5 сентября 2026

**Сделано**

- **Тексты 409.** `InvalidStateTransitionError` больше не называет статус заказа (утечка приватности §4.1: компания узнавала из ошибки, что заказ уже кто-то выполняет). Обе ошибки говорят по-русски: новый `orderEventLabels` в `shared/src/labels.ts`, статус предложения — через `offerStatusLabels`. Проверено unit-тестом по всем запрещённым парам «статус × событие» и e2e на отправку предложения в занятый заказ.
- **Завершённый заказ.** `OrderTransitionService.resolveOffer` ищет исполнителя по `EXECUTOR_OFFER_STATUSES` (с `COMPLETED`), поэтому повторные `confirm`/`submit` отвечают запрещённым переходом, а не неправдой «у заказа нет компании-исполнителя». Unit + e2e.
- **Предложение с карточки заказа.** Новое поле `OrderDetail.canSubmitOffer` (считает `order-view.ts` по настоящему статусу), `resolveCompanyActions` его пробрасывает, `SubmitOfferCard` показывает форму компании без предложения, `CompanyOfferCard` — кнопку «Отправить предложение» у отозванного и отклонённого. `offerHint` в этом случае не зовёт в ленту. Проверено в браузере на двух аккаунтах.
- **Файлы задания.** `companySeesTaskFiles` в `shared/src/offers.ts` — одно правило на список `OrderDetail.files` и на выдачу signed URL. `assertOrderParticipant` заменён на `assertFileAccess(orderId, viewer, ownerType)`: сдачи компании — только сторонам сделки, задание клиента — любой компании, пока заказ принимает предложения. Роль передаётся из контроллера, иначе задание одного клиента скачал бы другой.
- Прогоны: `npm run typecheck` и `npm run lint` чисто, **951 unit** (263 + 412 + 276), **131 e2e** (147 с, вне песочницы). Браузер: компания видит «Файлы клиента» и «Предложение по заказу» на свободном заказе, отправляет и отзывает предложение, у занятого чужого заказа ни кнопки, ни файлов нет. База возвращена `npm run db:seed`, серверы и Chrome закрыты.

**Принятые решения**

- Пункт 3 (предложение с карточки) → поле `canSubmitOffer` в API, а не кнопка «на авось» с 409. Решение пользователя.
- Пункт 4 (файлы задания) → открыть, пока заказ принимает предложения. Решение пользователя.
- Пункт 5 (тихое удаление заказа с предложениями) → отложено в подфазу **5.1**: уведомление требует снять `onDelete: Cascade` с `Notification.orderId`. Решение пользователя.
