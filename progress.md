# progress.md — журнал текущей фазы

Рабочий журнал между подсессиями **одной фазы**. Правила проекта, состояние кода и грабли — `CLAUDE.md`. План подфаз — `PLAN.md`. Требования — `MyBuild_NestJS_TZ.md`.

## Как этим пользоваться

**В начале подсессии:**

1. Прочитать этот файл целиком — здесь только текущая фаза, это быстро.
2. Посмотреть в `PLAN.md`, какая подфаза идёт следующей.
3. Прочитать раздел ТЗ, к которому она относится.
4. Взять **ровно одну** подфазу. Не больше.

**В конце подсессии:**

1. Дописать запись по шаблону ниже — четыре блока, ни один не пропускать.
2. Дать в чат короткий отчёт и указать: «в фазе N осталось: …» либо «фаза N завершена целиком».
3. Остановиться. Не спрашивать «делать дальше?».

**Правила для записей:**

- Новая запись добавляется **вниз**. Прежние записи этой фазы не переписывать.
- «Сделано» пишется только после проверки (`CLAUDE.md` §2). Тесты упали — так и написать, с выводом.
- Незаконченное уходит в «что дальше», а не замалчивается.
- Пишем состояние, а не историю: «сейчас работает так», а не «было А, стало Б».
- Без дат, без времени прогона тестов и без точных чисел тестов: всё это устаревает к следующей подсессии и врёт следующему агенту.

**Когда фаза закрыта целиком** (`CLAUDE.md` §9): свернуть записи в `CLAUDE.md` §6 (3–6 строк о том, что теперь есть), отступления — в §7, долгоживущие грабли — в §10, и **очистить этот файл** до шапки, шаблона и точки входа в следующую фазу. Летопись живёт в git, не здесь.

## Подфаза 5.1 — Backend: эндпоинты уведомлений

**Сделано**

- Модуль `backend/src/modules/notifications/`: контроллер, сервис, `dto/list-notifications.dto.ts`, чистый `notification-view.ts`. Подключён в `app.module.ts`. Четыре маршрута ТЗ §5:
  - `GET /notifications?unread=&page=&pageSize=` → `Paginated<NotificationDto>`;
  - `GET /notifications/unread-count` → `UnreadCount { count }`;
  - `POST /notifications/:id/read` → свежий `NotificationDto`;
  - `POST /notifications/read-all` → `MarkedRead { marked }`.
- Сортировка списка — в запросе: `isRead asc, createdAt desc`. Совпадает с индексом `(userId, isRead, createdAt)`. На фронте (5.4) сортировать нечего.
- Владение проверяет сервис (`updateMany` с `userId` в условии), а не `OwnershipGuard`: там `:id` — заказ. Чужое уведомление → **404**, не 403: 403 подтвердил бы, что строка есть. Не-uuid в `:id` тоже 404, до похода в базу.
- Ревизия `NotificationType`: все 11 значений кем-то создаются. 8 — state-машина, `FILES_UPDATED`/`AREA_VERIFIED` — `OrderWorkflowService`, `ORDER_DELETED` — `OrdersService.remove`. Закреплено тестом в `order-state-machine.spec.ts` («каждый тип кем-то создаётся»): он обходит таблицу переходов §4, собирает выданные типы и сверяет со списком тех, что создаются вне машины. Тип без источника и тип с двумя источниками одинаково роняют прогон.
- Уведомление компаниям при удалении заказа (было отложено, `CLAUDE.md` §7). `OrdersService.remove` теперь открывает транзакцию: `lockOrder` → читает предложения в `ACTIVE_OFFER_STATUSES` → условный `deleteMany` → `notification.createMany` с `orderId: null`. `OrdersService` получил в конструктор `OrderTransitionService` (цикла нет: тот зависит только от Prisma и машины).
- Две миграции: `20260905140000_order_deleted_notification` (`ALTER TYPE ADD VALUE`, отдельным файлом — грабля §10) и `20260905140500_notification_order_set_null` (внешний ключ `Notification.orderId` с `Cascade` на `SetNull`). Обе применены к живой базе.
- В `shared/`: `NotificationType.ORDER_DELETED` + подпись «Заказ удалён», типы `UnreadCount` и `MarkedRead`, комментарий к `NotificationDto.orderId` про `null`.

**Чем проверено**

- `npm run typecheck`, `npm run lint`, `npm test` — все три пакета зелёные (shared / backend / frontend).
- `npm run test:e2e` вне песочницы — 8 файлов, все зелёные. Новый `test/notifications.e2e-spec.ts` ходит по настоящему HTTP в живую Supabase: список, фильтр `unread` в обе стороны, порядок «непрочитанные выше», счётчик, `read-all` с повторным нажатием, 401 без токена, 400 на `unread=yes`, 404 на чужое уведомление и на мусор в `:id`, и два теста на удаление заказа — компания с активным предложением получает `ORDER_DELETED` с `orderId: null`, отозвавшая не получает ничего.
- Браузер не открывался: подфаза целиком backend, экрана у неё нет.

**Принятые решения**

- **Тип для «заказ удалён» — новое значение `ORDER_DELETED`** (решение пользователя). Переиспользовать `OFFER_REJECTED`/`OFFER_NOT_ACCEPTED` нельзя: заголовок берётся из типа, а выбора не было вовсе. Основание то же, что у двух прежних отступлений от списка ТЗ §3.
- **`orderId` у такого уведомления — `null`** (решение пользователя). Заказа нет, ссылка вела бы в 404; номер и название остаются в тексте. Отсюда `onDelete: SetNull` — и это же правило теперь распространяется на все уведомления удалённого заказа: они остаются в истории без ссылки.
- **`unread` в DTO объявлен строкой, а не `boolean`.** Иначе `enableImplicitConversion` делает `Boolean('false') === true`, и `?unread=false` означает обратное написанному. Разбор — в геттере `unreadOnly`, значения ограничены `@IsIn(['true','false','1','0'])`, всё прочее → 400.
- **`read-all` возвращает `{ marked }`, а не новый счётчик.** Счётчик после операции всегда ноль и ничего не сообщает; число помеченных даёт интерфейсу текст для тоста.
- **Сортировка списка на сервере, а не на фронте.** «Непрочитанные сверху» из 5.4 внутри одной страницы означало бы, что непрочитанное со второй страницы так и осталось внизу.
- **Уведомлений при удалении не получают компании с отозванным и отклонённым предложением** — для них заказ уже чужой (ТЗ §4.1).

**Что дальше**

- Следующая подфаза по `PLAN.md` — **5.2**, `OrderGateway`: Socket.io, namespace `/ws`, авторизация handshake по JWKS, комнаты `user:{id}` / `order:{id}` / `company-feed`, эмит событий ТЗ §8 после коммита. Источники готовы: `OrderTransitionService.apply` возвращает `fromStatus/nextStatus/notifications/offerUpdates`, новых заводить не нужно.
- Незакрытого в 5.1 нет. Единственное, что уехало в 5.4 по построению: раздел «Уведомления» обязан рисовать строку с `orderId: null` без ссылки.

**Где грабли**

- **`npm run db:migrate` (`prisma migrate dev`) на этой базе не работает вообще** — не только в песочнице. Падает с `P4002`: «Cross schema references… `public.User` points to `auth.users`». Это диагностика самого `migrate dev`, а не миграций. Рабочая команда — **`npm run db:deploy -w backend`** (`prisma migrate deploy`), она теневую базу не поднимает и применила обе миграции без замечаний. Таблицу команд в `CLAUDE.md` §6 надо править при закрытии фазы.
- **`enableImplicitConversion` сильнее собственного `@Transform`, а не слабее.** Проверено падающим тестом: `@Transform`, возвращающий `false` для строки `'false'`, проигрывает приведению по объявленному типу. Обходить это трансформацией бесполезно — надо менять объявленный тип поля. Спека `dto/list-notifications.dto.spec.ts` держит это правило.
- **Уведомления пишутся после `deleteMany`, а не до.** До удаления внешний ключ ещё указывал бы на живой заказ, и `SetNull` обнулил бы `orderId` тем же удалением — то есть результат тот же, но порядок скрытый. Закреплено unit-тестом на порядок вызовов.
- **`lockOrder` в удалении — не украшение.** Без блокировки компания успевает отправить предложение между чтением списка адресатов и `deleteMany`, и её предложение исчезает молча. Порядок блокировок тот же, что везде: заказ первым.
- **Рабочий каталог инструмента PowerShell переживает вызовы.** Один `cd backend` — и следующие `npm run typecheck`/`npm test` из корня запускаются в `backend`, отрабатывая только его скрипт и молча возвращая успех. Пути задавать абсолютные или возвращаться `Set-Location` явно.

## Подфаза 5.2 — Backend: `OrderGateway`

**Сделано**

- Новые зависимости backend: `@nestjs/websockets`, `@nestjs/platform-socket.io`, `socket.io`; `socket.io-client` — в devDependencies ради e2e. Требование ТЗ §2 и §8, без них шлюза не сделать.
- `shared/src/realtime.ts` — общий контракт: `WS_NAMESPACE`, `socketRooms`, `socketEvents` (все восемь событий §8), `socketMessages` (подписки клиента), типы нагрузок и `SubscribeAck`. `frontend/src/lib/socket.ts` больше ничего не объявляет сам — реэкспортирует это через `@/lib/types` и держит только `WS_URL`.
- `backend/src/modules/realtime/`:
  - `order.gateway.ts` — namespace `/ws`, авторизация handshake-токена (`auth.token`, запасной вариант — заголовок `Authorization`) тем же `SupabaseJwtService`, что и REST; проверка идёт middleware'ом namespace'а, поэтому отказ доезжает до клиента как `connect_error` с русским текстом. Комнаты: `user:{id}` — на подключении, `order:{id}` и `company-feed` — по сообщениям `subscribe:order` / `subscribe:feed` с ответом-ack. Плюс `emit`/`evict` — единственный выход в сокет.
  - `realtime-events.ts` — чистая сборка сообщений из `AppliedTransition`: кому какое событие, и кого выселить из комнаты заказа. Ни socket.io, ни Nest.
  - `realtime.service.ts` — фасад для сервисов: `orderCreated`, `transitionApplied`, `orderFilesUpdated`, `orderAreaVerified`, `notificationsCreated`. Ошибка рассылки не ломает ответ API (лог, не исключение).
  - `realtime.module.ts` — наружу отдаёт только `RealtimeService`; `AuthModule` импортируется явно.
- Врезка в существующие сервисы, всегда **после** коммита: `OrdersService.create` → `order:created`; `OrdersService.remove` → `notification:created` (и `createMany` заменён на `createManyAndReturn` — рассылать надо теми же строками); `OffersService.submit` → `offer:created`/`offer:updated` + переход; `OffersService.withdraw/reject`, `OrderWorkflowService.acceptOffer/confirm/dispute/submitWork` → переход; `addFiles` → `order:files_updated`; `verifyArea` → `order:area_verified`.
- `SupabaseAuthGuard` теперь пропускает контекст `ws` без проверок. Это не послабление: сокет авторизован в handshake, а глобальный guard на обработчике сообщения читал бы `headers` у объекта, которого там нет, — до правки каждое сообщение сокета падало с `TypeError` внутри `WsExceptionsHandler`, и ack не приходил вовсе.

**Чем проверено**

- `npm run typecheck`, `npm run lint`, `npm test` — все три пакета зелёные. `npm run build -w backend` и `-w frontend` проходят.
- Новые unit-наборы: `realtime-events.spec.ts` (адресация всех событий, выселение, отсутствие статуса и цены в нагрузке) и `order.gateway.spec.ts` (пять случаев авторизации, комнаты, рассылка без поднятого шлюза). В спеки сервисов добавлены проверки, что рассылки нет, когда действие не состоялось.
- `npm run test:e2e` вне песочницы — 9 файлов, 155 тестов, все зелёные. Новый `test/realtime.e2e-spec.ts` поднимает приложение через `app.listen(0)` и ходит настоящим `socket.io-client`: отказ без токена и с мусорным токеном, вход по живому токену Supabase, комнаты (свой заказ — пускает, чужой — нет, лента только компании), `order:created` после `POST /orders`, `offer:created` + `notification:created` с готовым заголовком, `order:status_changed` после предложения и — главное — проигравшая компания получает событие о своём предложении, но **не** получает `order:status_changed` о том, что заказ ушёл в работу, тогда как исполнитель его получает.
- Браузер не открывался: у подфазы нет экрана, клиент сокета появится в 5.3.

**Принятые решения**

- **Нагрузка событий про заказ — только идентификаторы** (`{ orderId }`, у предложений ещё `offerId`). Рассылка уходит в комнату целиком, а видимый состав заказа у клиента и у компании разный (ТЗ §4.1): положи в событие статус или цену — и одно сообщение обошло бы всю маскировку `order-view`. Событие означает «перечитай», данные по-прежнему приходят из REST. Исключение — `notification:created`: адресат один, скрывать нечего, и колокольчику (5.4) нужен готовый текст.
- **В комнату `order:{id}` пускаются клиент и компания с *активным* предложением**, а не «компании с предложением», как сказано в §8. Иначе компания с отозванным или проигравшим предложением получала бы настоящее движение заказа, который ей показывается как `WAITING`. По той же причине выселение из комнаты происходит **до** рассылки: принятие чужого предложения иначе успело бы рассказать проигравшей о переходе в работу.
- **`order:status_changed` шлётся только при настоящей смене статуса.** Второе предложение оставляет заказ в `AWAITING_CONFIRMATION` — перехода не было, а о самом предложении уже сказало `offer:created`.
- **`offer:created` против `offer:updated` различает вызывающий код**, а не машина: отправка предложения — upsert (§4.1), и после записи в базе всегда `SENT`. Признак — была ли строка до запроса, тот же, по которому считается `offerStatusBefore`.
- **Подписка на комнаты — явными сообщениями с ack**, а не автоматическая по роли. `company-feed` нужен только на странице ленты, комната заказа — только на его карточке; молчаливое членство означало бы, что каждая вкладка получает всё подряд. Отказ (`{ ok: false, error }`) не рвёт соединение: это не ошибка сокета, а «в комнату нельзя».
- **Удаление заказа не получило своего события.** В §8 его нет, а выдумывать не стали: компаниям с активным предложением уже уходит `notification:created` с типом `ORDER_DELETED`, и лента в 5.3 перечитывается по нему. Появится нужда в отдельном `order:deleted` — это решение пользователя.

**Что дальше**

- Следующая подфаза по `PLAN.md` — **5.3**, фронт: `lib/socket.ts` доводится до настоящего подключения (socket.io-client в зависимости фронта), подписка/отписка по страницам, обновление списков и карточки по событиям, оптимистичные мутации. Всё, что нужно, на сервере готово: имена событий и комнат — в `shared/`, ack на подписку отвечает «пустили или нет».
- Незакрытого в 5.2 нет.

**Где грабли**

- **Глобальные guard'ы попадают и на обработчики сообщений WebSocket.** `context.switchToHttp().getRequest()` в контексте `ws` возвращает сокет, а не запрос: `SupabaseAuthGuard` падал на `headers.authorization`, ack не приходил, и тест выглядел как зависший сокет, а не как ошибка. Новый guard обязан либо проверять `context.getType()`, либо сознательно работать в обоих контекстах.
- **Модуль обязан собираться сам по себе, а не полагаться на `@Global`.** `RealtimeModule` без явного `AuthModule` работал в приложении, но ронял `test/order-transition.e2e-spec.ts`, который собирает `OrdersModule` без `AppModule`.
- **e2e с сокетом требует `app.listen(0)`, а не `app.init()`.** Без слушающего порта подключаться некуда; порт берётся из `app.getHttpServer().address()`.
- **CORS сокета настраивается отдельно от HTTP.** `app.enableCors` на socket.io не распространяется, список читается из `CORS_ORIGINS` при каждом подключении: опции декоратора вычисляются при загрузке модуля, когда `.env` ещё не разобран. Клиент без заголовка `Origin` (тесты) пропускается — CORS защищает чужую вкладку, а не сервер.
- **Рассылка идёт строго после коммита.** `OrderTransitionService.apply` часто вызывается внутри чужой транзакции, и его результат надо вынести наружу (`submit`, `submitWork` теперь возвращают `AppliedTransition` из `$transaction`). Отправь событие изнутри — и откат оставит клиента с событием о том, чего не произошло.
- **Ошибка socket.io доезжает до клиента только текстом `message`.** Отсюда русские тексты прямо в `new Error(...)` шлюза: `connect_error` на клиенте — это `Error`, а не наш формат ответа API.

- `components/orders/order-live.tsx` — карточка заказа переехала в клиентское состояние. `OrderLive` держит `OrderDetail`, синхронизируется с серверным пропом сравнением по ссылке (в рендере, не в эффекте), сидит в комнате заказа и перечитывает его одним GET по событиям, отфильтрованным по `orderId`. Наружу отдаёт `useOrderSync()` → `{ apply, reload }`.
- Все восемь диалогов переведены с `router.refresh()` на `useOrderSync()`. `apply(order)` — там, где маршрут возвращает свежий `OrderDetail` (принятие, подтверждение, доработка, файлы, сдача, площадь); `reload()` — где ответ это `OfferDto` (отклонение, отправка и отзыв предложения) и после любого отказа. Вне карточки (списки `/available`, `/offers`) хук отдаёт запасной вариант — `router.refresh()`, поэтому те же диалоги работают в списках без изменений.

**Принятые решения**

- **Оптимистичность — мгновенным ответом сервера, а не предсказанием** (решение пользователя из трёх вариантов). Все шесть маршрутов сделки возвращают свежий `OrderDetail`, и карточка перерисовывается им сразу. Предсказывать нечего: цену сделки, номер сдачи, идентификаторы файлов и статусы проигравших предложений считает сервер, и вторая их реализация на фронте была бы большой поверхностью для расхождений. Откат при этом не нужен вовсе — врать пользователю нечем. Формально это отступление от буквы ТЗ §7 («обновляют UI оптимистично»): выигрыш предсказания перед ответом — время одного запроса.
- **Карточка заказа стала клиентской, списки остались серверными.** У карточки один объект и шесть маршрутов, которые его возвращают, — состояние окупается. У списков в адресе живут фильтр, поиск и страница, а приватность считает backend: пересобирать это в браузере значило бы завести вторую реализацию выборки. Поэтому списки просто перечитываются через `router.refresh()`.
- **Нагрузка событий не используется как данные, только как сигнал.** Из события берётся ровно `orderId` — чтобы отличить свой заказ от соседнего. Всё остальное приходит из REST, где приватность §4.1 уже посчитана.
- **Карточка заказа не слушает `notification:created`.** Уведомление — следствие того же действия, о котором уже сказало событие про заказ; слушать оба значило бы перечитывать её дважды. Списки `/offers` и `/available` слушают: там есть случай (удаление заказа), где события про заказ не будет вовсе.
- **Заказ, ушедший из ленты потому, что его взяла другая компания, событием не сопровождается.** Так решено ещё в 5.2 (чужое движение заказа компании не показывают), и лента догоняет это при следующем открытии. Своё предложение из ленты заказ уводит сразу — это своё же действие.
- **В комнату заказа фронт не просится, если знает, что не пустят.** Условие — `seesRealStatus` из `lib/order-access.ts`, то есть ровно то, что проверяет шлюз. Компания без активного предложения карточку открыть может, но real-time по ней не получает.

**Где грабли**

- **Правила React Compiler в eslint жёстче привычных приёмов.** `setState` в эффекте и присваивание `ref.current` в рендере — ошибки линтера, а не предупреждения. Поэтому «свежий обработчик без пересадки слушателей» сделан через `useEffectEvent` (стабилен с React 19.2), а сокет — модульным синглтоном вместо состояния.
- **Массив в зависимостях эффекта — это ссылка.** Список событий приходит пропом и на каждом рендере новый; эффект зависит от `events.join(" ")`, а имена внутри восстанавливаются `split`. Имена событий вида `order:created` пробелов не содержат — на этом всё и держится.
- **Комнаты socket.io не переживают переподключение.** Подписка обязана повторяться по событию `connect`, иначе после любого обрыва страница молча перестаёт обновляться: сокет жив, событий нет.
- **Личная комната приносит события по всем заказам пользователя.** Карточка одного заказа обязана фильтровать по `orderId` из нагрузки, иначе она перечитывается на каждое движение соседнего заказа.
- **Одно действие = несколько событий.** Принятие предложения шлёт `order:status_changed`, `offer:status_changed` на каждое проигравшее и уведомления. Без объединения в пачку (`createBurst`) это столько же `router.refresh()` подряд.
- **Синхронизация серверного пропа с состоянием делается в рендере, а не в эффекте.** `useState` + сравнение по ссылке (`state.server !== fromServer`). Через эффект между двумя рендерами показался бы кадр с устаревшим заказом.
- **`isolatedContext` у `new_page` даёт настоящие два окна с разными сессиями.** Без него обе вкладки Chrome делят cookie, и «две роли одновременно» не проверить. Это единственный способ пройти DoD 5.3 в браузере.
- **`performance.getEntriesByType("navigation").length` — надёжная проверка «без перезагрузки».** Скриншот этого не показывает: страница после `router.refresh()` выглядит так же, как после F5.
- **`npm run db:seed` после проверки обязателен.** Ручная проверка создаёт заказы и меняет предложения, а полный `npm run test:e2e` перепахивает базу ещё раз.
