# Проверка автономного демо MyBuild

Этап 2 принят пользователем. На этапе 3 добавлены проверки отказов хранения,
независимой сборки, ресурсов и HTTP-заголовков. Агент не запускал браузер:
пункты ниже являются ручной проверкой, а не отчётом об уже выполненных действиях.

## 1. Проверки без браузера

Из корня проекта после установки зависимостей:

```powershell
npm run typecheck
npm run lint
npm test
npm run test:demo-tools
npm run build:demo
npm run verify:demo
npm run verify:demo:clean
```

Первые три команды проверяют все пакеты и требуют полной установки (`npm ci`).
Для автономного frontend достаточно `install:demo` и команд с `-w frontend`
из его README. Ни одна из команд выше не запускает seed/reset или живые e2e.

Проверяются разрешённые и запрещённые переходы, полный цикл с доработкой,
атомарность, конкурентные записи, повторные команды, сохранение байтов файлов,
недопустимая роль, устаревшая форма, сброс, повреждение данных, квота и
восстановление после отказа. Новый таймаут не оставляет зависшую транзакцию
в ожидании навсегда. Отдельные экземпляры store проверяют независимость ролей
вкладок и чтение общих изменений без сетевого транспорта.

`verify:demo` проверяет 19 HTTP-маршрутов, ресурсы, HEAD, редирект с сохранением
query, 404, байты DXF и заголовки. Статический аудит читает все файлы экспорта:
ищет известные признаки прежних подключений и секретов, проверяет локальные
HTML/CSS-ресурсы, отсутствие серверных файлов и source maps. Это проверка
конкретных признаков, а не универсальный поиск любых возможных секретов.

`verify:demo:clean` создаёт временную копию только shared/frontend/scripts,
устанавливает зависимости по lockfile без lifecycle-скриптов, проверяет отсутствие
backend и Prisma Client, собирает и проверяет экспорт. Вместо прежних переменных
подставляются заведомо фиктивные маркеры; их отсутствие в экспорте проверяется.
После завершения копия удаляется. Нужен интернет для npm и build-time шрифтов.

Отчёты: `tmp/demo-audit.json`, `tmp/demo-clean-audit.json`. В них есть SHA-256
содержимого артефакта, размеры каждого начального ресурса, версии Node и дата.
Список HTML включает технические страницы Next.js и 404, поэтому их больше,
чем основных маршрутов HTTP-проверки. Хэши разных сборок могут отличаться.

## 2. Подготовка ручной проверки

```powershell
npm run preview:demo
```

Открыть **http://127.0.0.1:4173**. Остановка — `Ctrl+C`.
Не менять адрес на `localhost` посреди проверки: это другое origin и отдельные
локальные данные. Для проверки повреждений использовать отдельный временный
профиль браузера, где нет нужных локальных заказов.

## 3. Новая CSP и отсутствие обращений к старым сервисам

1. Открыть DevTools → Network, включить Preserve log и Disable cache.
   В Request blocking добавить `*onrender.com*`, `*supabase.co*`,
   `*supabase.com*`, `*cron-job.org*`; включить блокировку, обновить страницу.
2. На главной и в кабинете переключить тему, профиль; создать заказ,
   отправить предложение компанией, принять клиентом. Открыть уведомления.
   Скачать встроенный DXF; добавить свой допустимый PDF/изображение, сохранить,
   обновить страницу и скачать файл снова. Успех: действия выполняются,
   файлы открываются, в Console нет ошибок CSP или гидратации.
3. Проверить Network: **нет даже заблокированных попыток** к старым сервисам,
   нет Socket.io. Страницы, чанки, шрифты и пример документа идут с
   `127.0.0.1:4173`; пользовательский файл может скачиваться через `blob:`.
   Отсутствие запросов лучше проверить и без фильтра списка запросов.
4. У HTML-ответа проверить `Content-Security-Policy`, `X-Frame-Options: DENY`
   и `X-Content-Type-Options: nosniff`. У `/_next/static/...` проверить
   `Cache-Control: public, max-age=31536000, immutable`.

Правила лежат в `frontend/public/_headers`; локальный preview поддерживает
только используемое проектом подмножество формата. Целевой Vercel
использует корневой vercel.json; build:vercel проверяет соответствие политик.
Проверка применения заголовков Vercel относится к публикации.
[Конфигурация Vercel](https://vercel.com/docs/project-configuration/vercel-json).
Inline-скрипты Next.js и темы разрешены; CSP не блокирует произвольный внедрённый
inline-код. Встраивание PDF/HTML через iframe/object не используется.

## 4. Вкладки, сохранение и отдельный браузер

1. В первой вкладке выбрать Анну, во второй — СтройГрад. Создать заказ в первой,
   вернуться во вторую: заказ появляется, роль остаётся компанией. Отправить
   предложение и вернуться в первую: предложение видно, роль остаётся Анной.
2. Принять предложение, компанией сдать работу с файлом, клиентом вернуть на
   доработку, компанией пересдать, клиентом принять. Проверить уведомления и
   отсутствие чужих предложений у Ремонт Плюс. Повторный клик не создаёт дубль.
   Если это уже проверено при приёмке этапа 2, достаточно повторить короткий
   сценарий из пункта 3 под новой CSP.
3. F5 на карточке сохраняет роль, изменения и файлы. Назад/вперёд и фильтры
   работают. `/orders/view/?id=missing-test` показывает понятное отсутствие заказа.
4. В другом профиле браузера/инкогнито открыть тот же адрес и ссылку на новый
   заказ. Там исходный набор; локальный заказ из первого браузера не найден.
   Создать заказ здесь и убедиться, что он не появился в первом браузере.
5. «Выйти» не удаляет заказы. В отдельном тестовом профиле отмена подтверждения
   «Начать заново» сохраняет всё; подтверждение возвращает шесть исходных заказов.
   Другая открытая вкладка после возвращения видит сброс, не возвращает старый мир.

## 5. Ошибки хранения и файлов

1. Попытаться добавить файл больше 10 МиБ и файл с неподходящим содержимым
   (например, текст, переименованный в `.pdf`). Должно быть понятное сообщение,
   без добавленного документа. Удаление файла из черновика работает; документы
   уже выполненной работы не получают необоснованную кнопку удаления.
2. Логический лимит 50 МиБ и отказ IndexedDB из-за квоты проверены автоматически.
   Для проверки самого браузера можно в отдельном тестовом профиле добавить
   разные допустимые файлы суммарно больше 50 МиБ. Последняя операция отклоняется
   целиком, ранее сохранённые файлы доступны после F5. Заполнять диск не нужно.
3. Для несовместимого состояния в **отдельном тестовом профиле**, после первого
   открытия демо, выполнить в Console код ниже. Он заменяет только локальный
   демо-мир этого origin на неподдерживаемую версию. Затем нажать F5.

```js
const request = indexedDB.open('mybuild-autonomous-demo', 1);
request.onsuccess = () => {
  const db = request.result;
  const tx = db.transaction('world', 'readwrite');
  tx.objectStore('world').put({ version: 999 }, 'current');
  tx.oncomplete = () => { db.close(); console.log('Теперь обновите страницу'); };
};
```

Ожидается понятная ошибка версии вместо бесконечной загрузки. «Повторить» не
стирает состояние. «Продолжить без сохранения» открывает демо с заметным
предупреждением; после F5 снова видна ошибка версии, поскольку сохранённые
данные не перезаписаны. «Начать заново» после подтверждения восстанавливает демо.
Если настройки браузера позволяют запретить хранение данных сайта, отдельно
проверить тот же временный режим при запрете IndexedDB. Таймауты и отказ открытия
проверены автоматическими тестами; реальный запрет браузера ими не заменяется.

## 6. Внешний вид и клавиатура

Проверить светлую/тёмную тему на ширинах 390 и 1440 px: меню, карточку заказа,
формы, файлы и переключатель профиля. Не должно быть обрезанных действий и
горизонтального скролла страницы. Tab/Shift+Tab показывают фокус; Enter/Space
позволяют выбирать профиль и отправлять формы; Escape закрывает открытое меню.
Эти проверки можно совместить со сценариями выше.

## 7. Размер и скорость первого открытия

Статический аудит текущей сборки: около **448 КиБ** расчётного gzip для главной,
**439 КиБ** для входа, **513 КиБ** для кабинета. Учитываются HTML, подключённые
JS/CSS, preload-шрифты и eager-изображения. Это не сетевой замер: prefetch,
динамические чанки, выбранные браузером дополнительные шрифты и HTTP-заголовки
в эту оценку не входят. Локальный preview не сжимает ответы.

Крупнейшая картинка `landing-site.jpg` (327 966 байт) отмечена `loading="lazy"`;
реальный момент её загрузки выбирает браузер по расстоянию до viewport.
Пример DXF загружается по скачиванию; пользовательские Blob-файлы читаются
вместе с миром IndexedDB, но их байты не скачиваются с сервера.

Для воспроизводимого замера предложен профиль: Chrome без расширений,
DevTools Lighthouse → Navigation → Mobile → Performance, стандартное
simulated throttling Lighthouse. Для `/` и `/login/` выполнить по три прогона
с очисткой кэша/хранилища перед каждым; сохранить отчёты, версию Chrome,
настройки CPU/сети и медиану LCP. Для кабинета сначала выбрать роль, затем
измерить `/orders/` с отключённой очисткой хранилища, очищая только HTTP-кэш.
Не сравнивать этот прогон с гостевым как одинаковые условия.

Ориентир плана — LCP ≤ 2,5 с. **LCP ещё не измерен**, выполнение ориентира не
подтверждено. Локальные ответы без сжатия отличаются от будущего хостинга;
после публикации повторить тот же профиль на Vercel. При превышении ориентира
нужен отчёт с LCP-элементом и цепочкой запросов для адресной оптимизации.

## 8. Что сообщить после ручной проверки

Достаточно перечислить проверенные пункты и браузер. При ошибке указать URL,
выбранный профиль, последовательность действий и текст Console/Network.
Для скорости — медианы LCP и условия из пункта 7. Публикация остаётся
этапом 4; DNS при выбранном размещении на Vercel не меняется.
