# Публикация автономного MyBuild на существующем Vercel

По решению пользователя остаёмся на Vercel. Cloudflare, загрузка ZIP и изменение
DNS больше не входят в этап 4. Сохраняются существующий проект, подключённый
GitHub-репозиторий и адрес `mybuild.mydigitalhome.me`.

## 1. Что подготовлено в репозитории

Корневой `vercel.json` задаёт статическое размещение:

- Framework: **Other** (`framework: null`).
- Install Command: **`npm run install:demo`**.
- Build Command: **`npm run build:vercel`**.
- Output Directory: **`frontend/out`**.
- Завершающий слеш для маршрутов соответствует экспорту Next.js.
- CSP, запрет встраивания, nosniff, noindex, кэширование хэшированных файлов
  и скачивание DXF заданы в формате Vercel.

Next.js используется как сборщик HTML/CSS/JS. Node нужен во время сборки;
для просмотра не нужен сервер Next.js, NestJS или Supabase. Файл `_headers`
сохраняется для локального preview, но Vercel получает политику из `vercel.json`.
Перед каждой сборкой проверяется совпадение этих двух наборов заголовков.

`install:demo` устанавливает только shared/frontend и корневые зависимости,
отключает lifecycle-скрипты backend и явно включает build-time devDependencies,
даже при `NODE_ENV=production`. Node закреплён на **24.x** в package.json,
согласован с `.nvmrc`; новые зависимости не добавлены.

[Конфигурация Vercel](https://vercel.com/docs/project-configuration/vercel-json).

## 2. Сначала настрой существующий проект Vercel

Перед следующей публикацией запомни URL текущего рабочего deployment для отката.

В **Settings → Build and Deployment**:

1. **Root Directory** — корень репозитория. Удалить `frontend`, если он указан;
   поле оставить пустым (корень), сохранить. Это нужно, чтобы Vercel увидел
   корневой vercel.json, npm workspaces и shared.
2. **Framework Preset** — **Other**.
3. **Node.js Version** — **24.x**.
4. Команды и выходной каталог будут заданы `vercel.json` из новой версии кода.
   Для наглядности можно установить в панели те же значения из пункта 1.
   Не оставлять `.next` как выходной каталог новой сборки.

Новые Environment Variables не требуются. Старые API/WS/Supabase-переменные
исключаются сборщиком; после приёмки их можно удалить из этого frontend-проекта.
Переменные и настройки отдельного backend на Render не менять.

[Настройки сборки](https://vercel.com/docs/builds/configure-a-build),
[выбор Node.js](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions).

## 3. Опубликуй сначала без переключения основного домена

Чтобы проверить новый deployment отдельно, в существующем проекте открой:
**Settings → Environments → Production → Branch Tracking** и отключи
**Auto-assign Custom Production Domains** перед отправкой новой версии.
Текущий рабочий deployment продолжит обслуживать основной домен.

Затем обнови код в подключённом GitHub-репозитории своим обычным способом.
В опубликованной версии обязательно должны быть корневой `vercel.json`,
обновлённые package.json/package-lock.json, scripts и код автономного демо.
Локальные `frontend/out`, tmp и ZIP передавать в Git не нужно.

Дождись deployment со статусом **Ready**. В Build Logs должны выполняться
`npm run install:demo` и `npm run build:vercel`; последняя команда сама запускает
сборку и HTTP-проверки. Не должны выполняться Prisma generate, миграции или
запуск NestJS. При неудачной сборке пришли текст ошибки — домен ещё не переключён.

Если Vercel не запустил новую сборку автоматически, выбери deployment именно
с новой версией исходников и выполни **Redeploy**, отключив использование
старого Build Cache для первого перехода. Redeploy старого deployment
не подхватит локальные файлы, которых нет в его версии репозитория.

Передай агенту URL нового deployment `https://….vercel.app`. Он проверит HTTPS,
страницы и прямые ссылки, ресурсы, заголовки, 404 и DXF обычными HTTP-запросами,
без управления браузером. Если URL закрыт Vercel Authentication, проверку
публичных HTTP-ответов нельзя считать выполненной до предоставления доступа.
Не передавай пароли аккаунта.

Порядок staging и Promote описан в
[документации Vercel](https://vercel.com/docs/deployments/promoting-a-deployment).

## 4. Ручная проверка и основной домен

На адресе нового deployment проверь выбор профилей, создание заказа,
предложение компании, принятие клиентом, F5 и скачивание своего файла.
В Network не должно быть обращений к старому API, Supabase или Socket.io.
На каждой новой ссылке deployment отдельный IndexedDB: исходные заказы вместо
данных localhost ожидаемы. Подробности — [чек-лист](autonomous-demo-verification.md).

После успешной проверки в **Deployments** у проверенного staged deployment
открой **… → Promote** и подтверди назначение основного домена.
Сборка будет обслуживать **https://mybuild.mydigitalhome.me**. DNS, nameservers
и существующую привязку домена не менять. После этого повторить короткую проверку
на основном домене, включая прямой `/orders/view/?id=sample-4`, F5 и документы.

CSP может блокировать добавляемые хостингом инструменты preview, например Toolbar;
это не повод разрешать внешние источники приложению. Если такое происходит,
для проверки отключить соответствующий инструмент в проекте и повторить тест.

После приёмки можно вернуть **Auto-assign Custom Production Domains** для
обычных автоматических обновлений из production-ветки. Если оставить его
выключенным, новые версии продолжат требовать ручного Promote.

## 5. Откат и завершение этапа

При проблеме на основном домене использовать **Instant Rollback** на прежний
рабочий deployment. Не удалять его до приёмки. Откат возвращает ранее
развёрнутую версию без пересборки; настройки Root Directory и новые команды
при этом остаются настройками будущих сборок.
[Откат](https://vercel.com/docs/deployments/promoting-a-deployment#instant-rollback).

Повторить открытие после перерыва без посещений, например на следующий день.
Пингер не нужен. После подтверждения автономной версии пользователь может
отключить ненужный Render-сервис и оставшийся cron. Сам Vercel-проект продолжает
работать. Supabase и её данные автоматически не удалять.

## 6. Локальные проверки и границы результата

```powershell
npm run install:demo
npm run build:vercel
npm run verify:demo:clean
```

Проверяются конфигурация/совпадение заголовков, сборка, отсутствие известных
признаков прежних подключений в экспорте, HTTP-маршруты и ресурсы. Чистая проверка
повторяет install:demo/build:vercel в копии без backend, Prisma Client и .env,
с NODE_ENV=production и фиктивными старыми переменными подключения.

Это локальные проверки. Применение правил CDN Vercel и текущие настройки
аккаунта будут подтверждены после настоящего deployment. Сам агент ничего
в Vercel/GitHub/DNS не меняет. Старые Pages-архивы и package:demo остаются
необязательными локальными артефактами и для публикации на Vercel не нужны.
