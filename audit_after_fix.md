## Ошибок в самих исправлениях не найдено

Ни одно из закрытий не сломало то, что чинило, и не внесло регрессию в соседнее.
Отдельно проверялись места, где такое было наиболее вероятно:

- `escapeLike` — экранирование `\`, `%`, `_` идёт в правильном порядке; Prisma `contains`
  превращается в `ILIKE` с параметром, а стандартный escape-символ LIKE в PostgreSQL —
  обратная косая, то есть экранирование действует;
- `formatMoney` — разделитель разрядов действительно U+00A0, как заявлено в комментарии
  (проверено побайтово);
- `Semaphore` — `release()` вызывается в `finally`, отказ задачи слот не запирает;
- `custom_access_token_hook` — при отсутствии учётной записи `email_verified` становится
  `false` (`coalesce(..., false)`), при отсутствии профиля роль просто не добавляется,
  исключение не бросается;
- порядок guard'ов: глобальные (`SupabaseAuthGuard` → `RolesGuard`) выполняются до маршрутных,
  поэтому `ThrottleGuard` уже видит `request.user` и считает по пользователю, а не по IP.

## Фаза 1 — Доменная модель и state-машина

### Критические

Нет.

### Средние

**R1-С1. Отзыв предложения не создаёт ни одного уведомления.**
`backend/src/modules/orders/order-state-machine.ts:394` — `offerLeftSelection(OfferStatus.WITHDRAWN, null)`.
Компания отзывает предложение, заказ при этом может вернуться из `AWAITING_CONFIRMATION`
в `WAITING`, и клиент об этом не узнаёт: `Notification` не создаётся, `effects` содержит только
смену статуса предложения.
ТЗ §8 требует, чтобы событие, адресованное конкретному пользователю, одновременно создавало
`Notification`; `order:status_changed` в таблице §8 адресовано в том числе `user:{clientId}`.
Это тот же пробел, что закрытая находка `1-С2`, но для другого перехода.
*Рекомендация:* решить до 4.1 — там появится маршрут `POST /offers/:id/withdraw`.

**R1-С2. `OFFER_PRECONDITIONS` легко обойти порядком операций в Фазе 4.**
`backend/src/modules/orders/order-transition.service.ts:185-194` читает статус предложения
из базы **на момент вызова** `apply()`. Подфаза 4.1 (`POST /offers`, upsert-семантика ТЗ §4.1)
по плану сначала создаёт или обновляет `Offer`, и если запись уйдёт в `SENT` до вызова перехода,
то `OFFER_PRECONDITIONS[OFFER_SUBMITTED]` всегда увидит `SENT` и проверка перестанет что-либо
значить. Сейчас от этого частично спасает таблица переходов (из `IN_PROGRESS` события
`OFFER_SUBMITTED` нет вовсе), но правило «нельзя прислать предложение, когда уже работаешь»
держится не на своей проверке, а на побочном следствии.

**R1-С3. `OrderStateMachine.can()` не учитывает статус предложения.**
`order-state-machine.ts:446-448` смотрит только в таблицу переходов. По `PLAN.md` 4.4 состав
кнопок на странице заказа берётся именно из `can()`. Для заказа в `AWAITING_CONFIRMATION`
`can()` вернёт `true` для `OFFER_REJECTED` независимо от того, отклонено ли уже конкретное
предложение, — кнопка будет показана, а сервер ответит 409 `InvalidOfferStatus`.

### Низкие

**R1-Н1.** `backend/src/common/uuid.ts:10` — регулярное выражение требует версии 1–5 и варианта
`8|9|a|b`. Все нынешние идентификаторы — v4, проблемы нет; но любой переход на UUID v7
(или появление внешнего идентификатора) даст 404 на валидном UUID.

**R1-Н2.** `backend/prisma/seed.ts` начинается с BOM (U+FEFF); остальные файлы репозитория — нет.

## Фаза 2 — Аутентификация и доступ

### Критические

Нет.

### Средние

**R2-С1. `safeNextPath` пропускает управляющие символы — open redirect остаётся возможен.**
`frontend/src/lib/redirects.ts:15` проверяет только начало строки: `/`, не `//`, не `/\`.
Строка `"/\t/evil.com"` (в адресе — `%09`) все три условия проходит и возвращается как есть.
Дальше её получает разбор URL, а он по стандарту **вырезает** табуляцию, `\n` и `\r`:

```
new URL("/\t/evil.com", "http://app.local/login")  →  http://evil.com/
```

Проверено запуском (временный spec, удалён): три варианта — `\t`, `\n`, `\r` — дают внешний
адрес. Затронуты оба места, куда значение доезжает: `frontend/src/app/(auth)/callback/route.ts:42,47`
(`NextResponse.redirect(new URL(next, request.url))`, серверный редирект) и
`frontend/src/components/auth/login-form.tsx:42` → `resolveAfterAuthHref` → `router.replace(next)`.
Точка входа — `/login?next=%2F%09%2Fevil.com`: пользователь вводит настоящий пароль на настоящем
домене и после успешного входа уезжает на чужой сайт.
Сам браузерный переход в этом сеансе не воспроизводился — проверены фильтр и разбор адреса.
`frontend/src/lib/redirects.spec.ts` (7 тестов) этот класс входных данных не покрывает.

**R2-С2. Данные профиля не проверяются ничем, кроме формы в браузере.**
Единственный путь создания профиля — `supabase.auth.signUp` с публикуемым ключом
(`register-form.tsx:65`), метаданные оттуда забирает триггер `handle_auth_user_upsert`
(`20260903090000_auth_profiles/migration.sql:59-116`). Триггер проверяет только **наличие**
`role`, `firstName`, `phone` и `companyName` для компании. Формата и длины он не проверяет,
backend в этом пути не участвует вовсе. Правила из `shared/src/profile.ts` (`PHONE_PATTERN`,
`PHONE_MAX_LENGTH`) применяются только формой и `PATCH /profile`; запрос напрямую к
`/auth/v1/signup` кладёт в `public."User"` телефон произвольного вида и имя произвольной длины
(колонки `text`, верхней границы нет). Дальше эти значения показываются в интерфейсе,
а `companyName` попадёт в каталог подрядчиков (6.1).

## Фаза 3 — Заказы клиента

### Критические

Нет.

### Средние

**R3-С1. `GET /orders?page=` без верхней границы даёт 500.**
`backend/src/modules/orders/dto/list-orders.dto.ts:26-30` — у `page` есть `@Min(1)`, но нет
`@Max`. `Number.isInteger(1e20)` истинно, значит DTO пропускает `page=1e20`; сервис считает
`skip = (page - 1) * pageSize` (`orders.service.ts:155`) и передаёт в Prisma `2e+21`.
Проверено запросом к живой базе:

```
page 1e20  → skip 2e+21               → PrismaClientValidationError: Invalid `prisma.order.findMany()` … skip: 2e+21
page 9007199254740991 → skip 1.8e17   → OK, 0 строк
```

`PrismaClientValidationError` — не `HttpException`, поэтому `AllExceptionsFilter` превращает его
в 500 «Внутренняя ошибка сервера» и пишет стек в лог. Это тот же класс, ради которого в `shared/`
уже заведён `MAX_ORDER_NUMBER`, — просто для другого числа из пользовательского ввода.
Фронт от этого защищён (`orders-filter.ts:88-92` отбрасывает всё, что не безопасное целое),
API — нет.

**R3-С2. Текст ошибки Supabase Storage уходит клиенту.**
`backend/src/modules/files/storage.service.ts:49-51,66-68` кладёт `error.message` от Supabase
в `InternalServerErrorException`. `AllExceptionsFilter.toApiError` (`all-exceptions.filter.ts:48-54`)
для `HttpException` с объектным телом отдаёт `shaped.message` наружу как есть — то есть
собственная документация фильтра («Неожиданные исключения превращаются в 500 без подробностей»)
на этот путь не распространяется. Тот же класс проблемы, что закрытая находка `2-С1`.

**R3-С3. Скачивание seed-файлов отвечает 500 вместо понятного отказа.**
Файлы seed существуют только строками в БД (это задокументировано в `CLAUDE.md` §6). Проверено
запросом к живому бакету: `createSignedUrl` на отсутствующий объект возвращает
`StorageApiError: Object not found`. По коду `files.service.ts:164` → `storage.service.ts:66`
это 500 с текстом «Не удалось выпустить ссылку на файл: Object not found» (см. `R3-С2`),
а не 404. Пользователь демо, нажавший «Скачать» на seed-данных, получает тост с этим текстом.

### Низкие

**R3-Н1.** `backend/src/modules/files/files.service.ts:135-144` — внешний `catch` выполняет
`storage.remove(keys)` для **всей** пачки. Если исключение придёт не с загрузки, а из
`removeOrphanObjects` (а он делает запрос к базе, строкой 253), то удалены будут и объекты
только что созданных строк: строки останутся, объекты — нет.

**R3-Н2.** `frontend/src/components/orders/order-detail.tsx:229` — иконка выбирается по
`mimeType.startsWith("image/")`, а канонический тип DWG — `image/vnd.dwg` (`shared/src/api.ts:68`).
Чертёж DWG показывается иконкой картинки. В `file-dropzone.tsx:177` та же задача решена по
расширению и работает правильно — два разных правила для одного и того же.

**R3-Н3.** `shared/src/api.ts:47` — `'application/acad'` входит в `ALLOWED_FILE_MIME_TYPES`,
то есть в тип `AllowedFileMimeType`, но `FILE_EXTENSION_MIME` его никогда не возвращает
(`.dwg` → `image/vnd.dwg`). Значение живёт только в `MIME_ALIASES` как **входной** синоним.
Union шире, чем множество достижимых значений; `shared/src/api.spec.ts:43` проверяет вложенность
только в одну сторону и этого не ловит.

**R3-Н4.** `backend/src/common/filters/all-exceptions.filter.ts:53,60` — поле `error`
заполняется по-разному в зависимости от того, каким было тело исключения: для объектного —
`Not Found` (из Nest), для строкового — `HttpStatus[404]`, то есть `NOT_FOUND`. Единый формат
ошибки, обещанный ТЗ §5, соблюдается по составу полей, но не по их виду.

**R3-Н5.** `backend/src/modules/files/files.service.ts:110-116` и
`backend/src/supabase/supabase-admin.ts:92` содержат комментарии
`oxlint-disable-next-line no-await-in-loop`, но правило `no-await-in-loop` в
`backend/.oxlintrc.json` не включено (там только `correctness`, `suspicious`, `perf`).
Комментарии ничего не выключают.
